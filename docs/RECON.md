# 0단계 — 정찰 (Reconnaissance)

**목적**: 코드를 짜기 전에, 타깃 사이트들이 실제로 어떻게 생겼는지 사실을 확보한다.
Plan 모드는 읽을 것이 있을 때 잘 작동한다. 지금은 읽을 코드가 없으므로,
먼저 **읽을 데이터**를 만든다.

**모드**: 일반 모드 (Plan 모드 아님). Claude가 실제로 curl을 실행해야 하기 때문.
**모델**: Opus 5
**예상 소요**: 2~4시간 (사람은 대부분 지켜보기만 함)

## 프롬프트 2 — 편의점 4사 구조 조사

```
편의점 4사(CU, GS25, 세븐일레븐, 이마트24)의 상품 목록 페이지를 조사해줘.

각 사이트마다 다음을 확인하고 싶어:
1. robots.txt에서 상품 페이지 경로가 허용되는지
2. 상품 목록이 서버 렌더링(HTML에 이미 들어있음)인지, XHR/fetch로 나중에 불러오는지
3. XHR이라면 정확한 엔드포인트 URL, HTTP 메서드, 필수 파라미터, 응답 형식
4. 응답에 제품명·가격·이미지·카테고리·고유 ID가 들어있는지
5. 페이지네이션 방식과 전체 상품 수 (전체 카탈로그를 뜨는 데 몇 번 요청해야 하는지)

방법:
- curl로 직접 요청해보고 실제 응답을 확인해
- HTML만 오고 상품이 안 보이면, 페이지의 JS에서 호출하는 엔드포인트를 찾아봐
- 요청 사이에 최소 1초 간격을 둬
- 각 사이트의 원본 응답 샘플을 scratch/samples/<브랜드>_<설명>.<확장자> 로 저장해

주의:
- 아직 스크래퍼 코드를 작성하지 마. 조사와 샘플 저장까지만.
- 접근이 막히거나 봇 차단이 걸리면 우회하려 하지 말고 그 사실을 기록해.
```

> 💡 CU는 카테고리 이동이 `javascript:gomaincategory('10',1)` 같은 JS 호출로
> 되어 있어서 순수 HTML 요청으로는 상품이 안 보인다. Claude가 이 벽을 만나면
> 내부 엔드포인트를 찾도록 유도하고, 못 찾으면 Playwright 필요로 기록하게 한다.

## 프롬프트 3 — 카페 / 디저트 / 음식점 프랜차이즈

```
targets.yml에서 channel이 cafe, dessert, restaurant인 P0 브랜드들을 대상으로
같은 조사를 해줘.

프랜차이즈는 편의점과 성격이 다를 거야:
- 메뉴 수가 적고(수십 개) 페이지 구조가 단순할 가능성
- 대신 '신메뉴'가 메뉴판이 아니라 공지사항/보도자료에만 뜨는 경우가 많음

그래서 브랜드마다 두 경로를 모두 확인해줘:
  (a) 메뉴 목록 페이지 — 전체 카탈로그 스냅샷용
  (b) 공지사항 / 뉴스룸 / 보도자료 페이지 — 출시 소식 텍스트용

조사 결과 브랜드를 세 등급으로 분류해줘:
  EASY   — 정적 HTML 또는 깔끔한 JSON API
  MEDIUM — JS 렌더링 필요 (Playwright)
  HARD   — 인스타그램/앱 전용, 또는 봇 차단. 자동화 사실상 불가

샘플은 마찬가지로 scratch/samples/ 에 저장해줘. 코드는 아직 짜지 마.
```

## 프롬프트 4 — 마트와 식품 대기업

```
targets.yml의 channel이 mart, fmcg인 브랜드들을 조사해줘.

마트는 특히 확인이 필요한 게 있어:
- 이마트/롯데마트/홈플러스는 오프라인 매장 상품과 온라인몰 상품이 다를 수 있음
- 우리가 원하는 건 '신상품'이지 '온라인 할인상품'이 아님
- PB 브랜드(노브랜드, 피코크, 오늘좋은, 홈플러스시그니처)의 신상이 별도 페이지에
  모여 있는지 확인해줘

식품 대기업(fmcg)은 자사몰보다 뉴스룸/보도자료가 더 정확할 가능성이 높아.
어느 쪽이 신제품 정보를 더 빠르고 정확하게 주는지 비교해줘.

코스트코는 회원제라 접근이 어려울 것 같은데, 실제로 어떤지 확인만 해줘.
```

## 프롬프트 5 — 정찰 보고서

```
지금까지 조사한 내용을 scratch/RECON_REPORT.md 로 정리해줘.

포함할 것:
1. 소스별 표: 브랜드 / 채널 / 등급(EASY·MEDIUM·HARD) / 접근 방법 /
   엔드포인트 / 예상 요청 수 / robots.txt 상태 / 비고
2. 전체 카탈로그 스냅샷 1회에 걸리는 총 요청 수와 예상 소요 시간 추정
3. diff 방식이 잘 통할 것 같은 소스와, 통하지 않을 것 같은 소스 (그 이유도)
4. 제품 고유 ID를 제공하는 소스와, 이름 해시로 대체해야 하는 소스 구분
5. 지금 시점에서 가장 큰 리스크 3가지

그리고 sources/targets.yml 의 각 항목에 조사 결과를 반영해서 업데이트해줘.
(status를 unverified에서 verified/blocked로 바꾸고, 확인된 URL과 method를 채워넣기)
```

이 보고서가 정찰 단계의 최종 산출물이다.
**여기까지 오면 0단계 끝.** 이제 읽을 것이 생겼다.

## 1단계 — Plan 모드로 전환

`Shift+Tab`을 눌러 상태바에 `⏸ plan mode on`이 뜨는지 확인한 뒤:

```
scratch/RECON_REPORT.md 와 scratch/samples/ 의 실제 응답들, 그리고 CLAUDE.md를
전부 읽고 구현 계획을 세워줘.

계획에 반드시 포함할 것:
- CLAUDE.md 4장의 스키마가 실제 응답 데이터로 채워질 수 있는지 검증.
  안 되는 필드가 있으면 스키마 수정을 제안해.
- diff.py의 제품 동일성 판정 방식. 고유 ID가 없는 소스에서 같은 제품을
  같다고 판단할 근거가 뭔지 구체적으로. (제품명이 미묘하게 바뀌는 경우 포함)
- 첫 수직 관통(CU 하나로 전 구간 연결)에 필요한 파일 목록과 작성 순서
- 각 단계에서 "제대로 됐다"를 어떻게 확인할지

계획은 CU 하나만 다루는 범위로 좁혀줘. 나머지 소스는 이번 계획에 넣지 마.
```

계획을 읽을 때 볼 것:
- 정찰에서 확인한 **실제 사실**에 근거하는가, 아니면 일반론인가?
- CLAUDE.md의 원칙(특히 2.1 diff, 2.2 DB 없음)을 지키는가?
- 소스를 한 번에 여러 개 붙이려 하지 않는가?

납득되면 승인하고 구현으로 넘어간다. 이때부터는 **Sonnet 5**로 바꿔도 된다.

## 정찰 단계에서 흔한 함정

| 증상 | 대응 |
|---|---|
| Claude가 curl 안 해보고 "일반적으로 이런 구조입니다"라고 답함 | "실제로 요청해서 확인해줘"라고 되돌린다 |
| 조사하다 말고 스크래퍼를 짜기 시작함 | "코드는 아직"이라고 중단시킨다. 사실 확보가 먼저 |
| 봇 차단을 우회하려고 헤더를 조작함 | 즉시 중단. 막힌 곳은 HARD로 기록하고 넘어간다 |
| 샘플을 저장하지 않고 요약만 함 | 원본 파일이 없으면 나중에 재현이 안 된다. 반드시 저장시킨다 |
| 20개 소스를 한 번에 조사하다 컨텍스트가 터짐 | 채널별로 세션을 나눈다. 프롬프트 2/3/4를 각각 다른 세션에서 |
