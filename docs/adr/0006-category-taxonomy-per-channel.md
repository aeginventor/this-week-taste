# ADR-0006 자체 분류 목록은 채널 단위로 둔다

상태  채택
날짜  2026-08-14

## 맥락

`curate.py`가 LLM에게 자체 카테고리를 고르게 한다. 목록은 하나였고, CU 하나로
만들었으니 편의점 식품 기준이었다.

```
도시락, 김밥, 삼각김밥, 샌드위치, 버거, 샐러드, 면류, 즉석조리, 디저트,
과자, 아이스크림, 음료, 커피, 유제품, 주류, 안주, 기타
```

## 계기

2026-08-12 실측에서 **20건 중 8건이 `기타`로 떨어졌다.** 마스크팩·염색약 같은
생활용품과 복숭아·거봉 같은 신선식품이 목록에 아예 없었기 때문이다.
CU 카탈로그만 봐도 `생활용품`이 838건으로 7개 카테고리 중 세 번째다.

홈플러스(mart, 2,966건)가 붙으면서 이것이 더 커졌다. 마트 카탈로그는 과일·채소·
정육·수산물이 큰 축인데 목록에 하나도 없다. 그대로 두면 두 번째로 큰 소스의
분류가 통째로 `기타`가 된다.

## 결정

목록을 **채널 단위**로 나눈다. `curate.CATEGORIES_BY_CHANNEL`에 채널별 목록과
프롬프트 화자 설정(`편의점` / `대형마트` / `카페` / `식품 브랜드`)을 함께 둔다.
`publish.py`가 `sources.meta(source_id)["channel"]`을 넘긴다.

**소스가 아직 없는 채널(dessert, restaurant)은 만들지 않는다.**
그 채널의 소스를 붙일 때 실제 카탈로그를 보고 만든다.

## 결과

소스가 아니라 채널인 이유는 **분류가 우리 어휘이지 소스의 어휘가 아니기** 때문이다
(CLAUDE.md 7장). 같은 채널의 소스는 같은 목록으로 분류돼야 사이트 필터가 성립한다.
CU와 GS25가 서로 다른 분류 체계를 가지면 "편의점" 필터는 의미를 잃는다.

**감수하는 것** — 채널이 다르면 같은 제품이 다르게 분류된다. 홈플러스의 초코파이는
`과자`, 오리온의 초코파이는 `파이`다. 채널 간 비교를 하려면 나중에 상위 분류가
따로 필요하다. 지금은 주간 목록을 채널별로 보는 것이 전부라 문제가 되지 않는다.

**빠뜨렸을 때** — 목록 없는 채널을 만나면 `curate`는 예외를 던지지 않고 원본
카테고리로 발행한다(6장: 편집 품질보다 발행이 우선). 그래서 조용하다. 소스를
등록하는 시점에 `tests/test_curate_categories.py`가 잡는다.

**실측 (2026-08-14, cli 경로, 3채널 60건)**

| 소스 | 기존(편의점 17종) | 채널별 |
|---|---|---|
| homeplus (mart) | 기타 6/20, 9종으로 분산 | 기타 0/20, 13종 |
| starbucks (cafe) | 기타 0, 그러나 4종뿐 | 기타 0, 8종 |
| orion (fmcg) | 기타 0, 사실상 1종(과자 17 + 디저트 3) | 기타 0, 6종 |

마트에서만 `기타`가 문제였다. 카페·FMCG의 문제는 **분류가 뭉개지는 것**이었고
이건 `기타` 비율로는 보이지 않는다 — 오리온 20건이 전부 `과자`로 떨어져도
`기타`는 0이다. 사이트 필터 관점에서는 둘 다 똑같이 쓸모없다.

목록 밖 값은 60건 중 0건이라 출력 검증 코드는 넣지 않았다. 근거가 없다.

## 곁다리로 드러난 것

이 작업 중에 **상품 키를 LLM과 주고받던 것이 홈플러스에서 깨져 있었다**는 것을 찾았다.
itemNo가 앞자리 0을 가진 9자리 문자열(`070234705`)이라, 모델이 JSON으로 돌려줄 때
숫자로 해석하거나(`70234705`) 앞자리 0을 잃는다. 어느 쪽이든 키가 어긋나
**그 소스는 영영 편집되지 않는다.** 발행은 멀쩡히 되므로(원본 폴백) 조용하다.

통신에 쓰는 키를 배치 지역 참조(`r0`, `r1`, …)로 바꿨다. 모델이 할 일은 입출력을
짝짓는 것뿐이라 상품 키를 알 이유가 없었다. 프롬프트로 "숫자로 바꾸지 마라"를
덧붙이는 것보다 **숫자로 읽힐 여지가 없는 토큰을 쓰는 쪽**이 확실하다.

## 버린 대안

**소스별 목록** — 같은 채널의 소스가 서로 다른 분류를 갖게 되어 필터가 깨진다.
소스가 늘 때마다 목록도 늘어 관리 대상이 선형으로 증가한다.

**소스의 카테고리를 그대로 쓴다** — `category_raw`가 이미 있으니 LLM이 필요 없다.
그러나 소스마다 체계가 달라(CU 7개 / 홈플러스 123개 / 스타벅스 18개) 사이트에서
필터를 만들 수 없다. 정규화가 이 단계의 존재 이유다.

**하나의 큰 목록으로 통합** — 전 채널 카테고리를 합치면 60종이 넘는다. 모델이
편의점 도시락과 마트 정육을 같은 목록에서 고르게 되어 오분류가 늘고, 프롬프트도
길어진다. 채널을 이미 아는데 그 정보를 버릴 이유가 없다.
