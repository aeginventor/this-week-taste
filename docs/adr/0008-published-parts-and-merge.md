# ADR-0008 발행물을 소스별 부분과 병합본으로 나눈다

상태  채택
날짜  2026-08-24

## 맥락

`publish.run()`은 소스별로 실행되는데 출력 경로는 `data/weeks/<week>.json` **하나**였다.
`make week-all`을 돌리면 이렇게 된다.

```
cu 실행        → <week>.json 에 CU 결과를 쓴다
homeplus 실행  → 통째로 덮어쓴다   ← CU 사라짐
starbucks 실행 → 또 덮어쓴다      ← 홈플러스 사라짐
orion 실행     → 또 덮어쓴다      ← 스타벅스 사라짐
```

**마지막 소스 하나만 남는다.** `<week>.report.json`도 같다.
2.3이 "소스는 서로 격리한다"고 정했는데 발행 단계에서 그 격리가 깨져 있었다.

한 번도 드러나지 않은 이유는 발행이 한 번도 성공한 적이 없어서다. 소스가 하나였을 때는
증상이 없고, 넷이 된 뒤에도 실행이 안 됐다.

## 결정

**소스별로 쓰고 마지막에 합친다.**

```
소스별 run()  →  data/published/<week>/<source_id>.json     (부분, 커밋 안 함)
                            ↓ merge(week)
                 data/weeks/<week>.json                      (사이트가 읽는 파일)
                 data/weeks/<week>.report.json               (by_source로 지표 보존)
```

`make week-all`이 소스 루프를 다 돈 뒤 `publish --merge`를 한 번 부른다.
**한 소스가 실패해도 나머지로 합친다** — 여기서 멈추면 크롤러 하나가 깨졌을 때
그 주 전체가 발행되지 않는다.

### 발행 항목에 `source_id`를 추가한다

한 파일에 소스가 여럿 들어가는 순간 필요해졌다. `external_id`는 **소스 안에서만**
유일한데(4장), `publish.run()`이 지난주 항목을 `external_id`로만 찾고 있었다.
CU의 `gd_idx`와 오리온의 `goodsno`는 둘 다 숫자라 `"1234"`가 양쪽에 있을 수 있고,
그러면 **오리온 제품이 CU 제품의 `id`와 `first_seen`을 물려받는다.**
예외가 나지 않는다. 아카이브 URL이 조용히 다른 제품을 가리키게 된다([ADR-0001](0001-product-id.md)).

## 결과

**얻는 것** — 2.3의 격리가 발행 단계까지 이어진다. 소스별 지표가 `by_source`로 전부 남는다
(전에는 마지막 소스 것만 남았다). id 중복 검사가 **합친 뒤에** 한 번 더 돌아,
소스별로는 유일한데 합치면 겹치는 경우를 잡는다.

**감수하는 것** — 단계가 하나 늘었다. `make week`만 돌리면 부분 산출물만 생기고
사이트가 읽는 파일은 안 만들어진다. `make week-all`은 병합까지 하지만,
소스 하나만 돌릴 때는 `make merge`를 따로 불러야 한다.

`data/weeks/<week>.json`의 계약은 그대로다. `sources` 배열이 늘었을 뿐이라
`web/lib/weeks.ts`의 읽기 방식은 안 바뀐다.

## 버린 대안

**`run()`이 기존 파일을 읽어 자기 소스 항목만 갈아끼우기** — 파일이 하나로 유지된다.
하지만 "자기 소스 항목"을 골라내려면 결국 `source_id`가 필요하고, 실행 순서에 따라
결과가 달라진다. 재실행이 멱등이 아니게 된다.

**주차 파일을 소스별로 쪼개고 웹이 여러 개를 읽기** — 병합 단계가 없어진다.
하지만 `web/lib/weeks.ts`와 `docs/DEPLOY.md`가 전제하는 "주차당 파일 하나"가 깨지고,
아카이브 URL 하나가 파일 여러 개에 의존하게 된다.

**`id`를 조립해서 지난주를 찾기** (`make_id(source_id, external_id)`) — 스키마를 안 건드린다.
4장이 금지한 "id 역파싱"도 아니라 원칙 위반은 아니다. 하지만 `external_id`가 바뀐 적이 있는
항목은 `id`가 옛 값으로 이월돼 있어 못 찾는다. 그리고 **한 파일에 소스가 여럿 있다는 사실
자체가 항목에 기록되지 않아**, 사이트 필터나 나중의 DB 적재에서 같은 문제가 다시 나온다.
