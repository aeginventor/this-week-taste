# ADR-0011 한 주차의 스냅샷은 한 번만 뜬다

상태  채택
날짜  2026-08-24

## 맥락

2026-08-24에 수집 자동화([weekly.yml](../../.github/workflows/weekly.yml))가 처음 실제로
돌았다. 그리고 같은 날 첫 발행을 했다. 시각을 나란히 놓으면 이렇다.

```
14:24  사람이 W35를 발행한다      data/weeks/2026-W35.report.json  generated_at 14:24:41
15:30  봇이 W35를 다시 수집한다   snapshots/2026-W35/cu.json       scraped_at   15:30:44
```

**발행물이 근거로 삼은 스냅샷이 디스크에서 조용히 교체됐다.** 그날은 항목 차이가 0이라
(cu 4754 / homeplus 2861 / starbucks 330 / orion 114 전부 동일) 무해했지만, 두 가지가 남는다.

1. 카탈로그가 실제로 변한 뒤에 재수집하면 발행물과 스냅샷이 어긋난다. 발행물의 `added`
   103건이 지금 디스크에 있는 스냅샷에서는 나오지 않는 상태가 된다
2. **어긋났다는 것 자체를 알아낼 방법이 산출물에 없었다.** 리포트에는 `generated_at`만
   있고 무엇을 보고 발행했는지가 없다

이 창은 우연이 아니라 구조다. 수집은 봇이 월요일 KST 10:00에, 발행은 사람이 나중에
로컬에서 돌린다([8장 자동화 경계](../../CLAUDE.md)). 둘이 분리돼 있는 한 매주 열린다.

부수적으로, 사람이 `make week-all`을 돌릴 때마다 봇이 이미 뜬 카탈로그를
**294요청 다시 보내서** 떴다. 소스 서버에 대한 예의 문제이기도 하다(5장).

## 결정

**`snapshot.take()`는 그 주차의 스냅샷이 이미 있으면 다시 긁지 않고 그것을 쓴다.**
다시 뜨려면 `--refresh`(`make ... REFRESH=1`)를 명시해야 한다.

판단 근거는 **스냅샷 자기 자신의 존재**뿐이다. 발행 여부는 보지 않는다.

예외가 하나 있다. **이월본은 재사용하지 않는다.** `_hold_previous`가 이상 상황에서
지난주 스냅샷을 이번 주 자리에 복사하는데(2.4), 그건 "이번 주 데이터가 없다"는 뜻이다.
그걸 멱등 대상으로 삼으면 지난주 카탈로그가 이번 주의 최종 스냅샷으로 굳어버린다.
`held_from` 필드가 있으면 다시 긁는다.

재사용은 **로그로 시끄럽게 알린다**(2.4). 조용히 건너뛰면 "다시 긁었다"고 오해하게 되고,
그건 지금 고치려는 문제와 같은 종류의 실수다.

### 그리고 리포트가 무엇을 보고 발행했는지 남긴다

`<week>.report.json`의 `by_source.<source>`에 `snapshot` 블록이 실린다.

```jsonc
"snapshot": {
  "scraped_at": "2026-08-31T10:00:12+09:00",   // 이 발행이 근거로 쓴 스냅샷
  "count": 4754,
  "previous_week": "2026-W35",
  "previous_scraped_at": "2026-08-24T15:30:44+09:00",
  "held_from": "2026-W35"                       // 이월본일 때만 실린다
}
```

`held_from`은 해당 없는 소스에 아예 싣지 않는다. `monotonic_id`와 같은 규칙이다 —
7장의 `gd_idx_monotonic` 사고가 정확히 "해당 없는 자리에 실린 빈 값"이었다.

### 딸려 나온 것: 이월은 빈 자리만 채운다

`--refresh`를 만들고 나서야 보였다. `_hold_previous`는 이번 주 파일을 **무조건** 덮어쓰고
있었다. 그러면 다시 뜨다가 이상 상황에 걸릴 때 검증을 통과했던 이번 주 스냅샷이
지난주 것으로 되돌아간다. 흔적은 `held_from` 하나뿐이라 조용하다.

이월의 목적은 "이번 주 데이터가 없는 자리를 채우는 것"이므로, 이미 정상 스냅샷이 있으면
**채울 자리가 없다.** 이제 그 경우 이월하지 않고 기존 것을 유지한다. 이월본 자리에는
그대로 이월한다 — 이월본은 애초에 "데이터가 없다"는 뜻이라 지킬 것이 없다.

이 두 가지는 역할이 다르다. 멱등은 **어긋남을 막고**, 리포트의 근거는 **막지 못한
어긋남을 사후에 보이게 한다.** 재수집을 완전히 막을 수는 없으므로(`--refresh`가 있고,
데이터 저장소를 직접 만질 수도 있다) 둘 다 필요하다.

## 결과

**얻는 것**

- 발행이 본 카탈로그가 발행 후에 바뀌지 않는다. `data/weeks/<week>.json`과
  `snapshots/<week>/`의 관계가 시각으로 확인 가능해진다
- 사람이 `make week-all`을 돌려도 소스 서버에 요청이 나가지 않는다. 봇이 뜬 것을 쓴다.
  발행 전에 데이터 저장소를 `git pull` 하는 것이 이제 **선택이 아니라 전제**다
- 실패한 워크플로를 재실행하면 **성공했던 소스는 건너뛰고 실패한 소스만 다시 긁는다.**
  2.3의 격리가 재시도에도 적용된다

**감수하는 것**

- 일부러 다시 뜨려면 플래그가 필요하다. `--refresh`를 모르면 "왜 안 긁히지"로 막힌다.
  그래서 로그 메시지에 플래그 이름을 넣었다
- `take()`가 이제 "긁는다"가 아니라 "스냅샷을 확보한다"는 뜻이 됐다. 이름은 그대로 둔다
- 재사용 경로는 검증(카테고리 건수, 급감/급증)을 돌지 않는다. 저장돼 있다는 것이
  이미 통과했다는 뜻이므로 맞지만, **검증 기준이 바뀌어도 기존 스냅샷은 재검증되지 않는다**

## 버린 대안

**발행물이 있으면 `snapshot`이 거부한다** — 문제를 가장 직접 겨냥한다. 하지만
`snapshot.py`가 `data/weeks/`의 존재를 알아야 한다. [`paths.py`](../../pipeline/paths.py)가
못 박은 계층이 뒤집힌다 — 발행물은 파이프라인 **뒷단**이고, 그래서 `publish.py`가 자기
경로를 따로 갖는다. 2.2의 경계를 흐리는 대가로 얻는 것이, 자기 존재만 보고 판단하는
쪽과 같다.

**리포트에 근거만 남기고 재수집은 허용한다** — 계층을 안 건드린다. 하지만 어긋남을
*사후에* 알려줄 뿐 막지 않는다. 매주 열리는 창을 매주 사람이 확인해야 하고, 그건 9장이
말하는 "자동으로 할 수 있는 일에 사람을 넣는 것"이다. 요청 294건이 매번 다시 나가는
문제도 그대로 남는다.

**주차 디렉토리를 읽기 전용으로 만든다**(`chmod`) — 코드를 안 고친다. 하지만 실패
메시지가 `PermissionError`라 원인을 말해주지 않고, 데이터 저장소가 git으로 오가면서
권한이 유지되지 않는다.

**스냅샷 파일명에 시각을 넣어 여러 개를 남긴다**(`cu.2026-08-24T15:30.json`) — 아무것도
잃지 않는다. 하지만 "그 주의 스냅샷"이 하나라는 전제가 `diff.py`·`enrich.py`·
`previous_available`에 전부 박혀 있고, 그 전제를 푸는 대가로 얻는 것은 이미 무해하다고
확인된 이력이다. 원본은 `raw/`에 이미 남는다(2.5).
