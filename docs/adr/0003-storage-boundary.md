# ADR-0003 수집 데이터는 파일에, DB는 서빙 계층에만

상태  채택
날짜  2026-08-12

## 맥락

초기 설계는 DB를 아예 금지했다. `data/` 아래 JSON이 곧 데이터베이스이고
git 히스토리가 곧 아카이브다. 서버가 없으니 매주 운영 개입이 0분에 수렴한다.

그 규칙에는 유예 조항이 붙어 있었다.

> (검색·개인화가 실제로 필요해지는 시점에 재검토한다. 그 전에는 안 된다.)

## 계기

두 가지가 동시에 왔다.

**요구사항** — 상품마다 댓글을 달 수 있게 하기로 했다. 그리고 그 상품을 실제로
경험한 사람들의 글(블로그, 유튜브)을 상위 몇 개 링크하기로 했다.
전자는 사용자가 쓰는 데이터고, 후자는 외부에서 긁어와 캐시해야 하는 데이터다.
**둘 다 파일로는 안 된다.** 댓글은 동시 쓰기를 직접 막아야 하고, 이건 DB가
이미 트랜잭션으로 푼 문제다.

**목표** — 이 프로젝트는 포트폴리오를 겸한다. 목표 직무가 백엔드인데
현재 구조에는 서버도 DB도 API도 없다.

## 결정

DB를 도입한다. 단 **무제한이 아니라 경계를 긋는다.**

| | 저장소 | 이유 |
|---|---|---|
| 원본 응답 `data/raw/` | 파일 | 재처리용 아카이브. 조회하지 않는다 |
| 스냅샷 `data/snapshots/` | 파일 | 조회 패턴이 "주차별 전체 읽기" 하나뿐 |
| 발행물, 후기, 댓글 | DB | 낱개 조회, 검색, 쓰기가 생긴다 |

**금지: 스냅샷과 원본을 DB로 옮기는 것.** `snapshot.py`, `diff.py`, `enrich.py`는
DB를 import하지 않는다. 파이프라인은 DB를 몰라야 한다.

## 결과

판단 기준은 **조회 패턴**이다. DB의 강점은 인덱스로 "많은 것 중 몇 개"를 빨리 찾는 것인데,
스냅샷을 읽는 코드는 `diff.py` 하나뿐이고 그것도 항상 전체를 읽는다. 낱개 조회도,
검색도, 조건 필터도 없다. **강점이 쓰이지 않는 곳에 스키마와 마이그레이션과
연결 관리를 얹는 건 손해다.**

규모도 같은 방향을 가리킨다. 스냅샷은 소스 하나당 주 5,000건이다. 소스가 늘고
주가 쌓이면 수십만 행이 되는데, 그걸 전부 읽어 diff를 도는 것 외에 다른 접근이 없다.

**얻는 것** — 배치가 서빙을 모른다. DB가 죽어도 수집은 돌고, 스키마를 바꿔도
파이프라인은 안 건드린다. 파일 → DB로 옮기는 적재 단계 한 군데가 유일한 경계가 된다.

**감수하는 것** — 운영 부담이 늘어난다. 매주 0분이라는 목표는 이제 수집 파이프라인에만
적용된다. 서빙 계층은 사람이 쓰는 곳이라 성격이 다르다.

## 버린 대안

**전면 DB 이전** — 스냅샷까지 DB에 넣으면 파이프라인이 DB에 의존하게 되고,
그때부터 크롤러 하나를 고치는 데도 DB가 떠 있어야 한다. 얻는 것 없이 결합만 생긴다.

**Giscus 등 외부 댓글 위젯** — 정적 사이트를 유지하면서 댓글을 붙일 수 있다.
DB도 서버도 필요 없다. 하지만 방문자가 GitHub 계정이 있어야 해서 일반 사용자용으로는
쓸 수 없고, 백엔드를 만든다는 목표와도 어긋난다.
