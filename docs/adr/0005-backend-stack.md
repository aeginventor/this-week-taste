# ADR-0005 서비스 백엔드는 FastAPI로 시작한다

상태  채택
날짜  2026-08-12

## 맥락

[ADR-0003](0003-storage-boundary.md)에서 DB와 서빙 계층을 두기로 했다.
그러면 API 서버가 필요하고, 스택을 골라야 한다.

**수집 파이프라인이 Python인 것은 선택지가 아니다.** HTML 파싱, LLM SDK,
데이터 처리 생태계가 전부 Python 중심이다. 갈리는 것은 서비스 백엔드다.

| | FastAPI (Python) | Spring Boot (Java) |
|---|---|---|
| 런타임 | 파이프라인과 하나 | 둘로 나뉨 |
| LLM 연동 | 자연스러움 | 우회 필요 |
| 한국 SI·대기업 채용 | 약함 | 표준에 가까움 |
| 학습 곡선 | 낮음 | 높음 (DI, JPA, Gradle) |

이 프로젝트는 포트폴리오를 겸하고 목표 회사에 SI·대기업이 포함된다.
그쪽만 보면 Spring이 유리하다. 그리고 **Python 배치 + Java 서비스**는 실무에서
흔한 구조라 두 언어를 쓰는 것 자체가 억지도 아니다.

## 결정

**FastAPI로 먼저 만든다.** Spring Boot는 같은 API 계약을 다시 구현하는
별도 학습 과제로 뒤에 둔다.

## 결과

이유는 **순서**다. 동작하는 서비스가 먼저 있어야 "같은 API를 두 스택으로 만들어봤고
이런 차이가 있었다"는 비교가 성립한다. 아무것도 없는 상태에서 Spring부터 배우면
몇 주가 학습에만 들어가고 그동안 프로젝트는 멈춘다.

**얻는 것** — 파이프라인과 언어·저장소·의존성이 같다. 발행 스키마를 그대로
Pydantic 모델로 옮길 수 있다. 후기 수집과 홍보글 분류처럼 LLM이 들어가는 기능이
API와 같은 프로세스에 있다.

**감수하는 것** — Spring 경험이 당장 생기지 않는다. 채용 공고에서 Java/Spring을
요구하는 곳에는 이 프로젝트만으로 답이 안 된다.

## 지금 해둘 것

Spring 재구현이 뒤에 온다는 전제 때문에 **지금 지켜야 할 것이 하나 늘었다.**
API 계약(엔드포인트, 요청·응답 스키마)을 스택에 의존하지 않는 형태로 먼저 적는다.
그래야 재구현이 "같은 것을 다시"가 되고, 아니면 "비슷한 것을 새로"가 된다.

발행 항목의 `id`가 DB 외래키가 되므로 **id 불변 원칙([ADR-0001](0001-product-id.md))이
더 중요해진다.** 스택을 바꿔도 id 체계는 안 바뀐다.

## 버린 대안

**Spring Boot로 바로 시작** — 채용 정합성은 가장 높다. 하지만 학습에 몇 주가 들고,
그동안 수집 소스는 하나뿐인 상태로 멈춘다. 보여줄 데이터가 없는 백엔드는
백엔드 포트폴리오로도 약하다.

**Next.js API Routes** — 프론트와 한 저장소라 가장 빠르다. 하지만 파이프라인이
Python이라 언어가 셋이 되고, 백엔드 역량을 보여준다는 목적에는 가장 약하다.
