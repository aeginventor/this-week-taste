# 커밋 단위와 메시지

**커밋은 "저장"이 아니라 "이 변경을 하나로 되돌릴 수 있는 단위"다.**

## 단위를 정하는 기준

한 커밋이 하나의 완결된 변경이어야 한다. 판단해 볼 질문:

- 이 커밋만 되돌려도 나머지가 멀쩡한가
- 이 커밋만 보고 무엇이 왜 바뀌었는지 알 수 있나
- 제목에 "그리고"가 들어가야 하면 두 개로 나눠야 하는 신호다

**너무 크면** 되돌릴 때 필요 없는 것까지 딸려온다. 리뷰도 못 한다.
**너무 잘면** 히스토리가 소음이 되고, 중간 커밋들이 빌드가 안 되는 상태가 된다.

## 이 프로젝트의 첫 9개

수직 관통이 끝난 시점에 커밋이 하나도 없었다. 작업 순서대로 다시 쌓았다.

```
1  chore: 프로젝트 뼈대                        설정
2  docs: 설계 원칙 CLAUDE.md                   문서
3  docs: 정찰 결과 (브랜드 96개)
4  feat: 공통 기반 (주차 계산, 정규화, 알림, HTTP 세션)   아래층부터
5  feat: CU 스크래퍼
6  feat: 스냅샷 수집과 차집합 diff
7  feat: 상세 보강과 주차 발행
8  feat: 정적 사이트
9  data: 2026-W33 스냅샷 (cu)                  데이터는 따로
```

**아래층부터 쌓았다.** 4번(공통 기반)은 5~7번이 import하는 것들이다.
이 순서면 각 커밋 시점에 코드가 말이 된다. 반대로 쌓으면 중간 커밋들이
없는 모듈을 참조하는 상태가 된다.

**데이터 커밋을 코드와 섞지 않는다** (`CLAUDE.md` 9장). 9번은 파일 163개에
25만 줄이다. 이걸 코드와 섞으면 `git log -p`로 코드 히스토리를 볼 수 없다.
그리고 앞으로 매주 자동으로 쌓일 커밋이라 성격 자체가 다르다.

## 메시지

관례로 굳은 형식이 있다:

```
제목 (50자 이내, 마침표 없음)
                              ← 빈 줄 필수
본문. 72자에서 줄바꿈.
```

**빈 줄이 필수인 이유**: git은 첫 줄을 제목으로, 빈 줄 다음을 본문으로 취급한다.
`git log --oneline`, `git shortlog`, GitHub PR 제목이 전부 첫 줄만 쓴다.
빈 줄이 없으면 본문까지 제목으로 딸려간다.

**72자인 이유**: `git log`가 본문을 4칸 들여쓰기해서 출력한다. 터미널 80칸에
맞추려면 76자, 여유를 두면 72자다. **git은 자동 줄바꿈을 하지 않으므로**
안 끊으면 화면 밖으로 나간다.

## 본문을 언제 쓰나

**대부분의 커밋은 제목만으로 충분하다.** 이게 실제 관행이다.
여러 줄 본문은 "diff만 봐서는 왜 이랬는지 모르겠다" 싶을 때만 붙인다.

특히 이 프로젝트는 코드에 주석이 두껍다. `diff.py`의 docstring이 24줄이다.
커밋 본문에 같은 말을 또 쓰면 **나중에 한쪽만 고쳐지고 어긋난다.**

기준: **본문은 코드가 말하지 못하는 것만 적는다.**
- 왜 지금 이걸 했나
- 무엇을 일부러 안 했나
- 어떤 대안을 버렸나

이 저장소에서 본문이 붙은 첫 커밋은 `CLAUDE.md`의 DB 금지 원칙을 뒤집은 것이다.
그 결정의 이유는 파일 어디에도 안 남기 때문이다.

## 접두사 (conventional commits)

`feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:` ...

강제는 아니지만 있으면 `git log --oneline`이 훨씬 읽힌다.
자동으로 CHANGELOG를 만들거나 버전을 올리는 도구들이 이 규칙을 읽는다.

이 프로젝트는 `CLAUDE.md` 9장이 이미 `data:` 를 정해뒀으므로 거기 맞췄다.
