# 골든 테스트 (golden test)

**저장해둔 실제 응답을 정답지로 삼아, 파서가 그 정답을 계속 내는지 확인하는 테스트.**

## 문제 상황

스크래퍼는 남의 웹사이트 HTML을 읽는다. 그런데 그 사이트는 우리에게 예고하고 바꾸지 않는다.
클래스 이름 하나 바뀌면 우리 파서는 **에러를 내지 않고 빈 리스트를 돌려준다.**
`soup.select(".prod_list")`가 아무것도 못 찾으면 그냥 `[]`이지 예외가 아니기 때문이다.

이게 이 프로젝트에서 가장 무서운 실패다. 크래시는 눈에 띄지만 빈 결과는 안 띈다.

## 어떻게 하나

1. 정찰할 때 받은 진짜 응답을 파일로 저장한다 → `tests/fixtures/cu_productAjax_p1.html`
2. 테스트는 그 파일을 읽어 파서에 넣는다
3. 기대한 결과(상품 40개, 첫 항목의 이름과 가격)와 맞는지 본다

```python
SAMPLE = Path(__file__).resolve().parent / "fixtures" / "cu_productAjax_p1.html"

def test_parse_list():
    items, skipped = cu.parse_list(SAMPLE.read_text(encoding="utf-8"), ...)
    assert len(items) == 40
```

## 이게 주는 것

**파서를 고칠 때의 안전망.** 리팩터링하다 뭔가 망가뜨리면 즉시 알려준다.
네트워크를 안 타므로 0.1초에 끝나고, CU 서버가 죽어도 테스트는 돈다.

**소스 변경의 감지 장치.** 이건 좀 미묘하다. 골든 테스트는 저장된 파일을 쓰므로
CU가 오늘 사이트를 바꿔도 테스트는 그대로 통과한다. 감지는 실제 수집이 실패할 때
일어나고(`snapshot.py`의 건수 검증), 골든 테스트의 역할은 그 다음이다 —
새 응답을 받아 픽스처를 갱신하면 **테스트가 깨지면서 무엇이 어떻게 달라졌는지**를 보여준다.

## 이름의 유래와 다른 이름들

"golden"은 **golden file** — 정답으로 인정한 기준 출력물. 인쇄·영상 업계에서
최종 승인본을 golden master라 부르던 데서 왔다.

- **snapshot test** — Jest 등 프론트엔드 진영에서 쓰는 이름. 개념은 같다
- **characterization test** — 레거시 코드의 *현재 동작*을 그대로 박제할 때. 정답이
  맞는지는 따지지 않고 "지금 이렇게 동작한다"를 고정하는 용도

## 이 프로젝트에서

`CLAUDE.md` 7장은 "테스트를 위한 테스트"를 금지하면서 딱 세 가지만 허용한다:
`diff.py`, 정규화 로직, 그리고 파서 골든 테스트. 앞의 둘은 순수 로직이라 테스트가 쉽고,
골든 테스트는 **외부 세계와의 접점을 고정하는 유일한 수단**이라서다.

픽스처는 반드시 커밋해야 한다. 처음엔 `scratch/samples/`에 있었는데 그 폴더를
gitignore하면서 `tests/fixtures/`로 옮겼다. 픽스처가 저장소에 없으면 클론한 사람은
테스트를 돌릴 수 없고, 그러면 그건 테스트가 아니다.

## 한계

- **픽스처가 낡는다.** 저장한 시점의 응답이라 사이트가 바뀌면 현실과 어긋난다.
  갱신은 사람이 해야 한다
- **커버리지가 픽스처에 갇힌다.** 저장한 응답에 없는 형태(품절 상품, 가격 없는 항목)는
  영원히 테스트되지 않는다. CU 픽스처는 1페이지뿐이라 마지막 페이지의 항목 수가
  40개가 아닌 경우는 검증되지 않는다
- **용량.** HTML 응답은 크다. 이 프로젝트 픽스처 하나가 이미 수백 KB다
