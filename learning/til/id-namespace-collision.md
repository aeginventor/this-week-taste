# 식별자 네임스페이스 충돌

**같은 소스 안에서도 ID가 유일하지 않을 수 있다. 서로 다른 목록이 각자 1번부터 세기 때문이다.**

## 문제 상황

`CLAUDE.md` 4장은 `external_id`가 "소스의 전체 카탈로그에서 유일해야 한다"고 못 박고,
바로 아래에 이렇게 경고한다.

> ⚠️ 추측하지 말고 실측할 것.

이 경고를 처음 읽었을 때는 "바코드 같은 걸 쓰면 되는 거 아닌가" 싶었다.
2026-08-25에 소스 9곳을 붙이면서 **그중 8곳에서 충돌이 나왔다.**

| 소스 | 무엇이 겹쳤나 | 규모 |
|---|---|---|
| 배스킨라빈스 | `view.php?seq=` 와 `view_subcategory.php?seq=` 가 **둘 다 1부터 시작** | 128건 중 8건 |
| 던킨 | `props.products` 와 `props.productCats` 의 `id`가 별도 네임스페이스 | 216건 중 2건 |
| BBQ | 프로모션 카테고리(필릭스 PICK·추천)가 일반 카테고리와 상품을 공유 | 130건 중 25건 |
| 이마트24 | `ff`(Fresh Food)가 `pl`(차별화 상품)의 부분집합 | 727건 중 161건 |
| 맥도날드 | 세트가 버거와 맥런치에 함께 실림 | 110건 중 10건 |
| bhc | 카테고리 다섯이 서로 상품을 공유 | 158건 중 45건 |
| 도미노 | 신제품 섹션과 일반 섹션에 같은 상품 | 54건 중 4건 |
| 맘스터치 | `new` 탭이 다른 탭과 완전히 겹침 | 70건 중 4건 |

**전부 전체 카탈로그를 뜬 뒤에야 보였다.** 한 카테고리만 긁어보고 "ID 있네, 유일하네"
하고 넘어가면 100% 놓친다.

## 두 종류를 구분해야 한다

겉보기엔 같은 "ID 중복"인데 **대처가 정반대다.**

**① 다른 상품이 같은 키를 쓴다 (진짜 충돌)**

CU가 그랬다. 바코드가 16건 중복이었는데 **서로 다른 상품**이었다.
여기서 하나로 접으면 상품이 조용히 사라진다. → `ADR-0001`이 바코드를 주키에서 뺀 이유.

**② 같은 상품이 여러 번 실린다 (중복 노출)**

이마트24가 그랬다. 바코드·이름·가격이 **전부 같은** 항목이 14건 있었다.
소스가 한 상품을 두 목록에 노출한 것이라 접는 게 맞다.

가르는 법: **키가 같은데 다른 필드도 같은가.** 그래서 `emart24.py`의 `dedupe()`는
이렇게 짰다.

```python
if first["price"] != item["price"]:
    raise ParseError(f"같은 키({key})에 가격이 다르다: ...")   # ① 진짜 충돌
if first["name"] != item["name"]:
    log.info("이름 표기만 다르다 — 앞의 것을 쓴다")              # ② 목록별 절삭 차이
```

가격은 상품을 가르는 신호라 다르면 멈추고, 이름은 목록마다 자르는 길이가 달라서
(`손종원_new뉴욕스타일베이컨샌드` vs `…샌드위치`) 경고만 남긴다.

## 어떻게 막나

**접두사로 네임스페이스를 만든다.** 소스가 키를 두 체계로 주면 우리가 갈라준다.

```python
"external_id": f"{prefix}{seq}"       # p1124 (view.php) / s79 (view_subcategory.php)
"alt_ids": {"seq": seq}               # 소스 원본 값은 그대로 보존
```

`alt_ids`에 원본을 남기는 게 중요하다. `CLAUDE.md` 4장이 **"매칭은 원본 키로 하고
`id`를 역파싱하지 않는다"**고 한 것이 이 자리다.

**중복 노출은 순서를 정해 접는다.** 어느 카테고리가 분류를 가져갈지가 결과를 바꾸므로
`CATEGORIES`의 순서 자체가 사양이 된다.

```python
CATEGORIES = {"ff": "Fresh Food", "pl": "차별화 상품"}   # ff가 먼저 = ff 분류가 우선
```

이마트24에서 순서를 뒤집으면 Fresh Food 건수가 pl 목록 변동에 따라 출렁인다.
`BOOTSTRAP_COUNTS`가 흔들리면 매주 이상 경보가 뜬다.

## 왜 조용히 틀리나

이게 이 프로젝트에서 위험한 이유는 **예외가 안 나기 때문**이다.
diff는 키로 짝을 짓는데, 키가 겹치면 서로 다른 두 상품을 같은 것으로 보고
"변경 1건"으로 처리한다. 건수는 그럴듯하고 로그도 깨끗하다.

`snapshot.py`가 매 수집마다 유일성을 검사하는 이유가 그것이다 —
**깨지면 발행을 멈춘다.** 이 검사가 없었으면 BBQ를 붙인 주에 25건이 조용히 뭉개졌다.

## 한계

- **첫 수집 전에는 알 수 없다.** 실측이 유일한 방법이고, 그래서 소스를 붙이는 절차에
  "전체를 한 번 뜨고 유일성을 본다"가 들어가 있다(`.claude/skills/add-source/` 4절)
- **접두사는 되돌릴 수 없다.** `id`는 `first_seen` 주차에 확정되면 영구다(4장).
  접두사 규칙을 나중에 바꾸면 그 소스의 전 항목이 "단종 + 신상"으로 갈라진다
- **소스가 체계를 바꾸면 다시 터진다.** 던킨이 `productCats`를 없애고 `products`로
  통합하면 우리 `c` 접두사 키들이 전부 사라진 것으로 보인다
