# 요청 봉투 — 브라우저만 아는 요청 형식은 없다

> 걸린 자리: 버거킹. `POST /burgerking/BKR0632.json`에 빈 body를 보내면 HTTP 400이고,
> 정찰 기록은 **"브라우저에서 Payload 탭을 1회 캡처하면 풀린다"**로 끝나 있었다.
> `ADR-0009`가 "매주가 아니라 최초 1회인데도 밀려난 항목"이라고 이름까지 붙여둔 소스다.

## 1. 전문(傳文) 봉투가 뭔가

REST는 **URL과 메서드**로 "무엇을 할지"를 말한다. `GET /products/17`.

국내 기업용 프레임워크(여기서는 bizMOB)는 그러지 않는다. 엔드포인트를 하나로 두고,
**요청 본문 안의 코드**로 무엇을 할지 말한다. 그 본문이 봉투다.

```jsonc
{
  "header": {                    // 라우팅과 세션. 프레임워크가 정한 고정 모양
    "result": true,
    "error_code": "", "error_text": "", "info_text": "",
    "message_version": "", "login_session_id": "",
    "trcode": "BKR0632"          // ← 전문코드. 이게 "무엇을 할지"다
  },
  "body": { "menuKeywordList": [] }   // 그 전문의 파라미터
}
```

`trcode`는 은행·통신사 전산의 **전문코드** 전통이다. 앱 하나가 게이트웨이 한 곳에
붙고, 그 뒤의 여러 레거시 시스템으로 코드를 보고 갈라 보낸다. URL이 아니라 코드로
라우팅하니 **엔드포인트를 봐도 무슨 API인지 알 수 없다.** 버거킹의 `/burgerking/*.json`이
전부 POST이고 이름이 `BKR0632`인 이유가 이것이다.

응답도 같은 봉투로 온다. 그래서 **HTTP 200에 실패가 실려 온다** — `header.result`가
`false`인 200. 이걸 안 보면 빈 목록을 정상으로 삼킨다. `parse_envelope()`가
거기서 예외를 던진다.

## 2. 봉투는 어디에 적혀 있나

정찰이 "캡처해야 안다"고 본 것은, 요청 본문이 브라우저 안에서만 만들어진다고 봤기 때문이다.
그런데 **그 본문을 만드는 것도 JS이고, 그 JS는 우리도 받을 수 있다.**

```
burgerking_home.html   <script src="bizMOB/bizMOB-webExtend.js">   ← 프레임워크
                       <script src="/js/app.js">                    ← 앱 번들
```

읽어보니 세 조각이 각각 답을 갖고 있었다.

| 파일 | 알려주는 것 |
|---|---|
| `bizMOB-webExtend.js` | `requestTr`가 봉투를 만들어 **`message` 폼 필드 하나**에 넣고 POST한다 |
| `app.js` | 그 위에 `cd_call_chnn`(01 PC웹 / 02 앱 / 03 모바일웹)을 얹는다 |
| `js/KR_INT.js` (라우트 청크) | 화면이 실제로 부르는 전문과 body — `BKR0632 {menuKeywordList: []}` |

마지막 조각이 중요하다. 봉투 모양만 알면 `trcode`를 뭘로 채울지 모른다.
**어느 화면이 어느 전문을 부르는가는 라우트 청크에 있다.** webpack이 코드를 쪼개
`app.js`에는 청크 번호(`642: "KR_INT"`)만 남고 실제 호출은 그 청크 안에 있었다.

## 3. 그래서 순서가 바뀌었다

```
앱 번들(app.js·청크) → 프레임워크 JS → 그래도 모르면 브라우저 캡처
```

`.claude/skills/add-source/`의 0단계에 이 순서를 넣었다. Playwright가 최후의 수단인 것과
같은 이유다(CLAUDE.md 5장) — 브라우저는 느리고 잘 깨지는 데다, **한 번 캡처해서 알아낸
값은 왜 그 값인지 설명하지 못한다.** JS를 읽으면 봉투의 각 필드가 어디서 오는지가 같이 온다.

## 4. 이 방법이 안 통하는 경우

읽어서 재현할 수 있는 것과 없는 것이 갈린다.

- **재현된다** — 고정 봉투, 페이지가 HTML에 실어 보내는 토큰(gs25의 CSRF가 그렇다)
- **어렵다** — 서버가 준 값에 시각·비밀키를 섞어 서명하는 경우
- **버거킹에도 있었다** — `bizMOBWeb`에 `_bIsCrypto` 분기가 있어서, 켜져 있으면
  봉투를 AES-CBC로 암호화해 보낸다. 키가 JS에 있으니 따라 할 수는 있지만 훨씬 지저분하다.
  **이 사이트는 꺼져 있었다.** 켜져 있었다면 판단이 달라졌을 것이다

## 5. 남은 것

정찰 기록의 "다음 단계"는 **측량이 아니라 추정이다.** 이 프로젝트에서 이미 여러 번
어긋났고(파리바게뜨 `?cat1=`, 던킨 `/menu/all`), 이번엔 *난이도 자체*가 틀렸다 —
MEDIUM이 아니라 EASY였고, 전체 카탈로그가 요청 1건이었다.

"브라우저가 필요하다"와 "브라우저**만** 가능하다"는 다르다.
