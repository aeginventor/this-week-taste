# API의 날짜와 제품 번호는 무엇을 뜻하는가

이 글은 AI가 프로젝트 사례를 설명한 개념 기록이다. 작성자의 숙련도나 학습 소감을 대신 쓰지 않는다.
실제 조사와 공식 출처는 [2026-09-09 비교 연구](../../docs/data-route-study-2026-09-09.md)에 있다.

## 같은 모양의 날짜가 같은 사건을 말하지 않는다

식품 제조보고 API의 날짜를 받아 주차로 바꾸는 것은 쉽다. 그러나 보고가 발생한 주와
소비자에게 제품이 출시된 주는 다를 수 있다. JSON 형식을 올바르게 처리해도 서비스 답은 틀릴 수 있다.
API 계약은 필드의 타입뿐 아니라 **그 값이 가리키는 현실의 의미**를 포함한다.

이번 실험에서는 공식 발표 게시일인 8월 27일과 본문이 밝힌 출시 시점인 8월 28일을
분리했다. 푸드QR의 유효일, 피자헛 내부 데이터의 판매 가능 시작일도 출시일 자리에 넣지 않았다.
프로그램의 `date_basis`는 날짜를 어디서 얻었는지 남긴다. 게시일만 있으면 출시 연결을 보류한다.

## 번호를 연결하기 전에 단위를 확인한다

CU의 카탈로그 번호는 판매처의 목록 항목을 가리킨다. 바코드와 제조보고번호는 다른 단위다.
C005의 공식 문서 샘플에는 하나의 제조보고번호에 바코드 세 개가 있다.
단순히 같은 보고번호라는 이유로 합치면 여러 판매 단위를 하나로 지울 수 있다.

이런 연결을 관계형 데이터의 말로 표현하면 **일대일이 아니라 일대다일 수 있는 관계**다.
연결표를 만든다고 PostgreSQL을 바로 도입할 필요는 없다. 지금은 파일 속 후보 관계만으로
틀린 가정을 확인할 수 있었다. 기존 공개 ID는 그대로 두고 연결 근거를 따로 남긴다.

발표 제목의 상품명도 식별자는 아니다. 교촌의 동명 팝콘 발표와 현재 메뉴는 판매 장소와
규격·가격이 달랐다. 정확한 이름은 검색 후보를 좁힐 수 있지만 최종 동일성의 증명이 아니다.
전체 소스 카탈로그에서 이름 중복을 검사한 뒤에도 SKU 연결을 확정하지 않은 이유다.

## 변경분 조회에는 복구 범위가 있다

식품안전나라의 최신 공지는 API 변경분을 최근 7일로 제한하고 전체 CSV를 별도로 제공한다.
‘마지막 성공 이후 것만 받으면 된다’는 구현은 8일 이상 쉬었을 때 누락을 만들 수 있다.
여기서는 마지막 성공 시점이라는 체크포인트와 제공처가 복구해 주는 시간 범위를 함께 봐야 한다.
이번에는 도입하지 않았으므로 복구 구현 성능까지 검증했다고 말하지 않는다.

## 사례를 확인하는 것과 정확도를 재는 것은 다르다

알려진 CU 실패와 발표가 있는 스타벅스를 의도적으로 선택했다. 이런 표본은 결함과
가능성을 알아내기에는 좋지만 전체 출시의 정확도나 누락률을 추정하기에는 치우쳐 있다.
공식 발표 1개에서 신규·복귀를 구분했다고 모든 브랜드에서 잘 작동한다고 말할 수 없다.
다음 평가에서는 일정 기간의 공식 출시를 먼저 모은 뒤, 같은 제품이 각 경로에서 언제
발견됐는지 비교해야 한다. 못 찾은 것과 제품 연결이 모호한 것을 별도로 센다.

## 시간표와 연결

2026-09-09 기준, 제공된 시간표의 ‘판교캠퍼스 5층 시간표’ 시트 N열을 기준으로
7월 통계, 8월 Python·Spring Boot REST API 수업은 지난 일정이다. 날짜·키·표본의 의미를
확인하는 데 이 개념들을 연결할 수 있다. 지금은 LangChain 일정(9/9~11)이지만,
이번 문제의 원인이 체인 프레임워크 부재는 아니어서 도입하지 않았다.
RAG(9/18~22)·VectorDB(10/8)는 예정 수업이다. 검색된 문서와 확정 근거를 구분하는
문제는 이어질 수 있으나, 시간표만으로 사용자가 해당 기술을 이미 익혔다고 가정하지 않는다.
