# 모델이 같은 답을 내는 것과 맞는 답을 내는 것은 다르다

2026-09-10 공식 발표 자동화 개발 실험에서 Qwen3 8B는 같은 입력에 같은 JSON을 냈다.
그 JSON에는 같은 날짜 오류도 있었다. 8월 27일 글의 ‘오는 28일’을 9월 28일로 해석했다.
재현성은 결과를 다시 조사할 수 있게 하지만, 정확성을 보장하지 않는다.

## 역할을 나눈 이유

발표는 첫 문장에서 두 음료를 함께 소개하고, 뒤 문단에서 하나는 신규 출시이고 다른 하나는 매년 돌아온다고 설명했다.
같은 문장 안의 ‘출시’만 찾는 규칙은 이 관계를 놓쳤다. LLM은 관계를 구분했지만 달력 계산을 틀렸다.
그래서 연구 코드에서는 다음처럼 나눴다.

| 책임 | 입력과 확인 방법 |
|---|---|
| 모델: 제품과 사건을 연결 | 제품명·사건 종류·날짜 표현·근거 문단을 추출한다. 의미가 맞는지는 평가 자료와 대조한다 |
| 코드: 달력 계산 | 지원하는 명시 월일 또는 ‘오는 N일’을 기사 게시일 기준으로 계산한다. 게시일 자체를 출시일로 쓰지 않는다 |
| 코드: 근거 위치 검사 | 발췌가 지정한 문단에 있는지, 특징 단어가 인용한 문단에 있는지 확인한다 |
| 코드: 카탈로그 연결 | 브랜드·이름·종류·판매 맥락·구체적인 특징을 조합한다. 이름만으로는 연결하지 않는다 |

모델이 말한 날짜와 코드가 계산한 날짜를 둘 다 남긴다. 인용한 문단에서 찾을 수 없는 특징을 버린 내역도 기록한다.
없는 근거를 사람이 결과 JSON에 채워 넣은 것이 아니라, 코드의 변환 규칙과 원시 출력을 보존한 것이다.

이 검사에도 한계가 있다. 문단에 날짜와 제품이 있다는 사실만으로 그 날짜가 그 제품의 출시일이라는 뜻은 아니다.
행사 기간을 잘못 선택하면 달력 계산은 정확해도 사건 판단은 틀린다. 따라서 형식 검사만으로 의미 평가를 대신할 수 없다.

## 개발 자료와 평가 자료

호지 라떼 발표를 읽고 프롬프트와 코드를 고쳤다면, 그 발표에서 맞힌 결과는 개발 결과다.
새로운 발표에서도 잘 처리하는지는 손대지 않은 평가 자료로 확인해야 한다.
AI가 원문을 읽어 만든 정답 후보도 오류가 있을 수 있으므로, 독립적인 사람의 검수라고 쓰지 않는다.
이번 합성 할인·금융상품·명령 삽입 사례는 회귀 방어를 확인했을 뿐 실제 발표 분포를 대표하지 않는다.

## 수업과의 연결

9월 10일을 기준으로 시간표 N열의 통계·Python·REST API 관련 과목은 지난 일정이고, LangChain 과정은 9월 9~11일에 걸쳐 있다.
이는 시간표 분류이며 학습자의 숙련도 판정이 아니다.
통계의 표본·분모 구분은 ‘개발 기사 1편’을 전체 발표 정확도로 확대하지 않는 데 쓰였다.
API 계약은 로컬 모델의 요청 설정·JSON 응답·실제 토큰·종료 상태를 기록하는 데 쓰였다.
프롬프트는 사건과 근거를 요청하는 계약으로 사용했지만, 그 지시만으로 날짜 오류를 막지는 못했다.
단일 HTTP 호출과 파일 재현으로 충분해 LangChain 구조를 추가하지 않았다.
