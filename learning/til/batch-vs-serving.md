# 배치 계층과 서빙 계층

**주기적으로 데이터를 만드는 쪽(배치)과, 사용자 요청에 답하는 쪽(서빙)은 다른 시스템이다.**

## 두 계층이 왜 다른가

| | 배치 | 서빙 |
|---|---|---|
| 언제 도나 | 주 1회, 정해진 시각 | 사용자가 올 때마다 |
| 실패하면 | 다음 주에 다시 하면 됨 | 사용자가 에러를 봄 |
| 느리면 | 3분이든 30분이든 상관없음 | 200ms도 길다 |
| 데이터 접근 | 전체를 한 번에 읽음 | 한 건을 빨리 찾음 |
| 상태 | 없음 (매번 처음부터) | 있음 (세션, 캐시) |

**요구사항이 정반대다.** 그래서 같은 저장소, 같은 언어로 짜더라도
설계를 섞으면 양쪽 다 나빠진다.

## 이 프로젝트에서

지금은 배치만 있다.

```
[배치] snapshot → diff → enrich → curate → publish → data/weeks/*.json
                                                          ↓
                                              빌드 타임에 읽어 정적 HTML 생성
```

서빙이 아예 없다. Next.js가 **빌드할 때** JSON을 읽어 HTML을 전부 만들어두고,
사용자는 그 HTML만 받는다. 서버에서 도는 코드가 0이다.

댓글과 후기가 들어오면 이렇게 된다:

```
[배치] Python  →  파일(원본, 스냅샷)  →  적재  →  DB
                                                  ↑
                                    [서빙] API  ←─┘  →  웹
```

## 무엇을 파일에 두고 무엇을 DB에 둘 것인가

`CLAUDE.md` 2.2가 정한 경계다. 판단 기준은 **조회 패턴**이다.

**파일에 두는 것 — 스냅샷, 원본 응답**

스냅샷은 소스 하나당 주 5,000건이다. 소스가 늘고 주가 쌓이면 수십만 행이 된다.
그런데 이걸 읽는 코드는 `diff.py` 하나고, 그것도 **"이번 주 전체와 지난주 전체"를
통째로 읽는다.** 낱개 조회도, 검색도, 조건 필터도 없다.

DB의 강점은 인덱스로 "많은 것 중 몇 개"를 빨리 찾는 것이다. 전체를 다 읽을 거면
그 강점이 쓰이지 않는다. `json.load()` 한 번이면 되는 일에 스키마, 마이그레이션,
연결 관리를 얹는 건 손해다.

**DB에 두는 것 — 발행물, 후기, 댓글**

댓글은 사용자가 **쓴다**. 파일로 하려면 동시 쓰기를 직접 막아야 하는데,
그건 DB가 이미 트랜잭션으로 해결한 문제다.

발행물은 "이 상품 하나"를 찾는 조회가 생기고, 검색이 붙고, 댓글이 외래키로 매달린다.
전형적인 DB 작업이다.

## 이 분리가 주는 것

**배치가 서빙을 모른다.** `snapshot.py`, `diff.py`는 DB를 import하지 않는다.
그래서 DB가 죽어도 수집은 돌고, 스키마를 바꿔도 파이프라인은 안 건드린다.

**적재(load)가 명시적인 단계가 된다.** 파일 → DB로 옮기는 코드가 한 군데 생기고,
그게 유일한 경계다. 여기만 보면 두 세계가 어떻게 연결되는지 알 수 있다.

## 업계 용어로

이 구조를 **ETL** 또는 **ELT**라고 부른다.

- **E**xtract — 소스에서 뽑는다 (`snapshot.py`)
- **T**ransform — 정규화하고 비교하고 정제한다 (`diff.py`, `curate.py`)
- **L**oad — 서빙용 저장소에 적재한다 (아직 없음)

그리고 배치가 만든 결과를 서빙이 읽기만 하는 이 패턴은
**CQRS**(읽기와 쓰기 모델 분리)의 아주 단순한 형태로도 볼 수 있다.
