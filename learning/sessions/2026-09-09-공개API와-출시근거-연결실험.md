# 공개 API를 찾았지만 출시 근거는 별도로 필요했다

> 2026-09-10 정리: 아래는 당시 판단과 실패를 보존한 기록이다. 기사 개선은 중단하고 [동결 코드와 재현 안내](../../research/launch-study-20260910/README.md)로 분리했다.

날짜: 2026-09-09. [상세 조사·공식 출처·실험 조건](../../docs/data-route-study-2026-09-09.md).
앞선 [첫 설계 검토](2026-09-09-발견과-출시를-분리한-설계-검토.md),
[ADR-0018](../../docs/adr/0018-discovery-and-launch.md)과 [0019](../../docs/adr/0019-publication-input-integrity.md)의 후속 작업이다.

## 이번에 확인하려던 문제

중복 등록을 제거해도 ‘실제 신상품을 충분히 찾아오는가’는 남았다. 사용자는 공개 API를
사이트 내부 JSON과 구분하고, 기존 수집 방식과 공식 발표를 같은 사례로 비교하도록 요청했다.
기존 구조 유지나 API 도입을 먼저 정하지 않았다.

## 사실과 선택

- **확인한 사실:** C005 최신화 중단, I1250의 행정 날짜, 푸드QR의 유효 날짜, HACCP 명세의 바코드 검색 부재를 공식 문서에서 구분했다. 현재 API 운영 공지는 예전 설명보다 제약이 컸다.
- **실험 사실:** CU 중복 2건은 현재 카탈로그로 식별할 수 있다. 스타벅스 발표는 신규 음료와 시즌 복귀를 구분하지만 기사에는 제품 번호가 없다. 실제 상품 API 조회는 하지 못했고 문서 샘플 미일치를 전체 부재라고 판단하지 않았다.
- **AI 추천:** 공식 발표 연결의 추가 가치를 먼저 격리 검증하고, 포장식품 API는 키 확보 뒤 상품 연결을 별도로 시험한다. 소스별 대체 결정은 유보한다.
- **사용자 결정:** 다음 첫 단위로 ‘카탈로그 + 공식 발표 연결 실험’을 선택했다.
- **미결정:** 시즌 복귀의 공개 범위, 신규 공식 소스의 운영 도입·이용 조건 승인, API에 의한 수집 대체, 실제 운영 품질 목표.

## 구현과 확인

[카탈로그·문서 비교](https://github.com/aeginventor/this-week-taste/blob/10865a188e631a4810dfe223ce9b98f488e31aa2/scripts/compare_data_routes.py)와
[출시 근거 연결](https://github.com/aeginventor/this-week-taste/blob/10865a188e631a4810dfe223ce9b98f488e31aa2/scripts/link_launch_evidence.py)은 연구 전용이며 stdout에만 출력한다.
AI가 공식 본문에서 수동 정리한 주장과 프로그램의 연결 후보를 별도로 표시했다.
문서와 주장에 다른 ID를 두고 게시일·사건일·날짜 근거를 분리했다.

4개 소스 전체 4,528항목을 이름 중복 검사 문맥으로 사용했다. 선택한 8항목에서
호지 라떼의 신규 출시와 블랙 라떼의 시즌 복귀가 각각 정확 이름 후보가 됐다.
아이스 변형은 식별 부족, 퓨어 호지차는 프로모션 언급, 교촌 팝콘은 다른 판매 맥락으로 보류했다.
나머지 CU 2건·피자헛은 이번 발표 표본에 근거가 없다. 공개 출시 확인으로 승격한 항목은 없다.

같은 입력의 재실행 출력은 바이트 단위로 같았다. 문서 변경, 다른 브랜드, 중복 이름,
게시일 오인 등 [회귀 테스트](https://github.com/aeginventor/this-week-taste/blob/10865a188e631a4810dfe223ce9b98f488e31aa2/tests/test_launch_evidence_experiment.py)를 확인했다.
전체 `make test`: 648 passed, 3 skipped. 이는 자동 출시 추출의 품질 지표가 아니다.
운영 프롬프트·파이프라인·웹을 변경하지 않았으므로 수집·LLM 실행·사이트 재발행은 하지 않았다.

격리 자료는 `/private/tmp/taste-api-study-20260909/`에 있다.
작업 시작 시 기존 파일 199개의 지문과 비교해 학습 목차 링크를 추가한 `learning/README.md`
이외의 기존 파일이 그대로임을 확인했다. 비공개 데이터 저장소의 Git 상태도 깨끗했다.
실행 요약은 격리 경로의 `validation.json`에 남겼다.
원문은 공개 문서에 복제하지 않고 최소 사실·공식 URL·검증 조건을 남겼다.
이번 추가 구현을 제거하면 이전 운영 코드로 돌아간다. 기존 데이터·ID·URL의 마이그레이션은 없다.

## 실제로 쓴 개념

[API 데이터 의미](../til/api-data-semantics.md): 날짜의 의미는 타입 검사만으로 지켜지지 않는다.
식별자 연결은 이름 비교보다 엄격해야 하고, 목적 표본의 결과를 전체 정확도로 해석하면 안 된다.
7일 증분 범위는 실패 복구 설계에 직접 영향을 준다. 학습 때문에 프레임워크나 DB를 추가하지 않았다.

## 블로그 초안 — 작성자의 관점은 보완 필요

첫 수정에서는 CU에 새 번호로 등록된 기존 상품 두 건을 보류했다. 그러나 이것은
실제 출시를 잘 찾는 수집 체계의 증명이 아니었다. 다음 조사는 공개 API가 그 빈자리를
채울 수 있는지 확인하는 데서 시작했다.

공식 데이터라도 서비스의 질문과 답이 같지는 않았다. 제조보고의 날짜는 출시일이 아니었고,
바코드 API 중 하나는 최신화가 중단돼 있었다. 표시정보 API는 상품을 연결할 가능성이 있었지만
인증 조회 전이라 일치율을 계산할 수 없었다. 오래된 문서보다 최신 운영 공지를 확인하는 과정도 필요했다.

발표 자료에서는 다른 종류의 정보를 얻었다. 같은 주 목록에 등장한 두 음료 중 하나는 신규,
다른 하나는 계절 복귀였다. 하지만 아이스 변형의 제품 번호까지 발표가 증명하지는 않았다.
따라서 프로그램은 정확 이름의 연결 후보와 보류를 분리했다. 사람이 읽어 정리한 주장을
자동 추출 결과처럼 보고하지 않았고, 공개 사이트의 출시 확인 상태도 바꾸지 않았다.

작은 실험은 결합 방식의 가능성과 남은 경계를 함께 보여줬다. 카탈로그는 판매 항목,
공개 API는 제조·표시 연결, 발표는 출시 사건에 강점이 있었다. 어떤 경로를 운영에 넣을지는
실제 일치 결과와 이용 조건, 감당할 검토 비용을 더 확인해야 한다.

`[작성자 보완: API 실조회보다 발표 연결 실험을 먼저 선택한 이유를 자신의 말로 2~3문장.]`

## 포트폴리오에 남길 수 있는 것

- 문제: 등록·제조보고·출시라는 서로 다른 사건을 혼동하면 형식상 정상인 데이터로 오답을 만든다.
- 사용자 기여: 공개 API의 뜻과 검토 범위를 명확히 하고, 발표 연결을 첫 실험으로 선택했다.
- AI 기여: 공식 계약 조사, 표본 대조, 연구 코드·회귀 테스트 작성, 한계와 출처 기록.
- 검증 결과: 목적 표본 8개에서 정확 이름 후보 2개·의미/동일성 보류 3개·해당 발표 근거 없음 3개를 구분했다. 반복 실행 일치와 문서 변경 거부를 확인했다.
- 주장하지 않을 성과: 실제 출시 정확도 상승률, 전체 커버리지, 운영 시간 절감, API 상품 조회 성공. 자동 추출도 아직 구현하지 않았다.
