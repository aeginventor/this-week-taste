## 1. "CU 하나로 2주 검증"이라는 게이트

### 무엇이 문제였나

`CLAUDE.md` 8장은 이렇게 정해두고 있었다.

> 3단계를 건너뛰고 4단계로 가지 않는다. diff가 쓸모없다면 소스 20개는 쓰레기 20배다.

의도는 맞다. 신상품 판별의 핵심이 diff인데 그게 부정확하면 소스를 늘려봐야
쓰레기만 늘어난다. 먼저 CU 하나로 2주를 돌려 품질을 확인하자는 것이다.

문제는 **소유자가 이 사실을 모르고 있었다는 것**이다. 원하던 건 여러 브랜드의
주간 신상이었고, 당장 이번 주에 보고 싶어 했다.

### 왜 오늘 볼 수 없나

여기서 중요한 걸 알게 됐다. **스크래퍼가 없어서가 아니라 비교 대상이 없어서다.**

이 프로젝트의 신상품 정의는 "소스가 NEW라고 붙인 것"이 아니라
"지난주엔 없었고 이번 주엔 있는 것"이다. 그래서 어떤 소스든:

```
1주차 수집  →  발행 없음 (기준선)
2주차 수집  →  첫 신상품 발행
```

`diff.py`에 이게 코드로 박혀 있다. 지난주 스냅샷이 없으면 전부 빈 결과를 쓰고
`baseline: True`를 남긴다. 주석에 이유가 적혀 있다 —
"전량을 신상으로 내보내는 일은 어떤 경우에도 하지 않는다."

### 결정

**발행 게이트는 유지하되, 기준선 수집은 게이트 밖으로 뺐다.**

근거는 이거다. 소스마다 기준선 주차가 따로 필요하므로,
**소스 추가를 한 주 미루면 그 소스의 첫 결과도 정확히 한 주 밀린다.**
검증을 기다리는 동안 아무 소스도 안 뜨면, 검증이 끝난 뒤 또 한 주를 기다려야 한다.

원래 규칙이 걱정한 것은 맞지만 대상이 틀렸다. 위험한 건 스크래퍼가 아니라
**diff의 판정 품질**이고, diff는 소스와 무관한 코드다.
스크래퍼를 묶어두는 것으로는 그 위험이 줄지 않는다. 발행을 묶어두면 줄어든다.

### 버린 대안

**소스의 NEW 라벨을 쓰는 것.** 이러면 오늘 당장 볼 수 있다. 하지만 실측이 말린다 —
CU는 671건에 NEW를 붙여놨는데 실제 이번 주 신상은 30건이었다. **22배 과다**다.

다만 반대 방향은 흥미롭다. `added_not_labelled`가 0이었다. 즉 diff가 신상이라고
판정한 것 중 소스가 NEW를 안 붙인 건 하나도 없었다. **NEW 라벨은 진짜 신상의
상위집합**이라는 뜻이고, 그래서 정밀도 필터로는 못 쓰지만 **재현율 채점표로는 완벽하다.**
`snapshot.py`가 라벨을 `.control.json`으로 분리해 보관하는 이유가 이거다.

스타벅스는 `new_SDATE`(예: `20260608`)라는 **실제 출시일**을 준다.
이건 라벨이 아니라 날짜라 검증 가능하다. 나중에 다시 볼 만하다.

## 2. "DB를 도입하지 않는다"

### 무엇이 문제였나

`CLAUDE.md` 2.2가 Postgres/SQLite 등의 도입을 금지하고 있었다.
`data/` 아래 JSON이 곧 DB이고 git 히스토리가 곧 아카이브라는 설계다.
매주 운영 개입 0분이라는 목표에는 최적이다.

그런데 소유자가 원하는 기능 중에 **댓글**이 있었다. 사용자가 쓴 걸 저장해야 하니
상태가 생기고, 정적 사이트로는 불가능하다.

그리고 더 큰 문제가 있었다. **이 프로젝트는 포트폴리오를 겸한다.**
목표 직무가 AI 백엔드 서비스 엔지니어인데, 지금 구조에는 백엔드가 없다.
서버도 DB도 API도 인증도 없다. 보여줄 표면적이 0이다.

### 결정

**개정하되 경계를 그었다.** 그냥 "DB 도입 허용"으로 바꾸면 파이프라인까지
DB로 끌려가서 설계가 무너진다.

| | 저장소 | 이유 |
|---|---|---|
| 원본 응답 | 파일 | 재처리용. 조회하지 않는다 |
| 스냅샷 | 파일 | 조회 패턴이 "주차별 전체 읽기" 하나뿐 |
| 발행물, 후기, 댓글 | DB | 낱개 조회, 검색, 쓰기가 생긴다 |

판단 기준은 **조회 패턴**이다. DB의 강점은 인덱스로 "많은 것 중 몇 개"를 빨리 찾는 것인데,
스냅샷은 항상 전체를 읽으므로 그 강점이 쓰이지 않는다.

같이 뒤집은 것: 7장의 "사용자 계정 v1 범위 밖" → v2 범위로,
6장 LLM 역할에 후기 홍보/일반 판별과 보도자료 레코드 추출 추가.

### 6장에 조건을 하나 붙였다

새로 추가한 두 역할은 앞의 넷과 성격이 다르다. 1~4번은 이미 있는 레코드를 다듬는 일이라
틀려도 표시가 어긋나는 정도지만, 5~6번은 **없던 레코드를 만들어낸다.**
그래서 이 둘은 결과를 그대로 쓰지 않고 근거(원문 URL, 판별에 쓴 문구)를 함께 남기기로 했다.

## 3. 백엔드 스택

### 선택지

수집 파이프라인이 Python인 건 협상 대상이 아니다.
BeautifulSoup, LLM SDK, 데이터 처리 생태계가 전부 Python이다.

갈리는 건 서비스 백엔드다.

| | FastAPI | Spring Boot |
|---|---|---|
| 런타임 | 파이프라인과 하나 | 둘로 나뉨 |
| AI/LLM 연동 | 자연스러움 | 우회 필요 |
| 한국 SI/대기업 채용 | 약함 | 압도적 |
| 학습 곡선 | 낮음 | 높음 (DI, JPA, Gradle) |

목표 회사 중 하나가 SK AX라 Spring이 유리한 면이 크다.
그리고 **Python 배치 + Java 서비스**는 실무에서 흔한 구조라 억지도 아니다.

### 결정

**FastAPI로 먼저, Spring Boot 재구현은 별도 학습 과제로.**

이유는 순서다. 동작하는 서비스가 먼저 있어야 "같은 API를 두 스택으로 만들어봤다"는
비교가 성립한다. 없는 상태에서 Spring부터 배우면 몇 주가 학습에만 들어가고
그동안 프로젝트는 멈춘다.
