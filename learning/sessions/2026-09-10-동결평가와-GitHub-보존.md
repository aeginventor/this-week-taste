# 개발에 쓰지 않은 공식 발표를 읽혔더니, 날짜 검증이 정답을 지웠다

> 2026-09-10 정리: 아래는 당시 판단과 실패를 보존한 기록이다. 기사 개선은 중단하고 [동결 코드와 재현 안내](../../research/launch-study-20260910/README.md)로 분리했다.

2026-09-10. 사용자 승인에 따른 일회성 비공개 평가이며 공개 발행·배포·정기 수집은 하지 않았다.
선행: [개발 실험](2026-09-10-로컬모델-출시근거-자동화.md), [수집 프로토콜](../../docs/launch-automation-protocol-2026-09-10.md), ADR [0016](../../docs/adr/0016-press-feed-sources.md)·[0018](../../docs/adr/0018-discovery-and-launch.md)·[0019](../../docs/adr/0019-publication-input-integrity.md).

## 결론

**현재 방식은 추가 개선이 필요하다. 운영 도입 준비로 넘어가지 않는다.**
자료 확보는 동작했지만, 개발에 사용하지 않은 실제 문서 11편에서 유용한 최종 메뉴 계열 연결은 0건이었다.
오연결도 0건이지만, 연결하지 못한 결과이므로 정확한 연결기라는 근거가 아니다.
원문에서 제품·출시 사실·일 단위 날짜를 확인할 수 있는 언급 10건 중 원시 모델 출력은 1건을 담았고, 코드 처리 후에는 그 1건도 날짜가 사라졌다.
10건 중 9건은 최초 출시인지 재출시인지 불명확하다. 이를 ‘진짜 신제품 10개’ 또는 시장 누락률로 표현하지 않는다.

사용자는 기존 자료 보존·두 저장소 커밋과 푸시·정해진 기간의 일회성 비공개 확보를 승인했다.
자료의 분할·AI 정답 후보 작성·구현과 평가·추가 개선 추천은 AI가 수행했다. 독립적인 사람의 정답 검수와 실제 검토 시간 측정은 수행하지 않았다.
시즌 재출시의 공개 범위는 미결정이다.

## 자료를 얼마나 확보했나

SCK COMPANY 공식 분류의 게시일 2026-08-01~09-08을 대상으로, 제목으로 출시 글을 골라내지 않고 기간 내 목록을 확보했다.

| 확보 단계 | 관측 |
|---|---:|
| 목록 페이지 | 3페이지, 각 12개 카드 |
| 기간 안에서 발견한 URL | 16개 |
| 본문 확보 | 16개: 새 요청 15개 + 기존 사본 재사용 1개 |
| 실패 | 발견한 16개 URL 안에서는 0개 |
| 공백 정규화 후 같은 본문 | 1쌍 → 고유 본문 15개 |
| 개발용 | URL 5개, 고유 본문 4개 |
| 최종 평가용 | 고유 문서 11개 |
| 요청/시간 | 목록 3 + 본문 15 + robots 1 = 19요청, 약 22.98초 |

목록 3페이지에서 모든 카드가 기간 시작일보다 과거임을 확인하고 멈췄다. 최대 5페이지·본문 40개를 넘기지 않았고, 기존 Session의 순차 요청·최소 1초 간격과 받은 robots를 따랐다.
목록에서 빠진 기사, 이미지에만 있는 설명, 전체 시장의 미발표 상품은 이 분모에 들어 있지 않다.
HTML 전체는 보존했고 모델 입력은 본문의 p/h2/h3/li 텍스트다. 표·이미지 내용까지 전부 해석했다고 주장하지 않는다.

기존 8월 27일 호지 라떼 발표 두 URL은 공백 차이만 있는 같은 본문이었다. 원시 지문은 달랐지만 정규화한 본문은 같아 기존 사본을 기준으로 중복을 제외했다.
9월 2일·3일·7일의 이미 읽은 문서도 개발용으로 분리했다. 모델 결과를 보고 평가 문서를 교체하지 않았다.

## 무엇을 정답 후보로 삼았나

AI가 원문을 읽고 **모델 평가 전에** 문단 근거와 불확실성을 저장했다. 독립적인 사람의 검수 자료가 아니다.
동결 시각은 2026-09-10 11:42:54 KST다.

- 평가 목록 지문: `6059f10069495f79bacace65f883b6b108c47304d5af309bdbcc16090a2e2318`
- 정답 후보 지문: `262b8c0b58289e90652742178c382c7c2003c93a37817d9a6560987617bb5790`
- 프롬프트 지문: `1ba3cf4e905ead55e3d9af286cbf8ff043075e9c5a01a3b00f4e044b2f8c4444`
- 모델: Qwen3:8b Q4_K_M, Ollama 0.33.3. `temperature=0, seed=41, num_ctx=8192, num_predict=4096, think=false`.
- 카탈로그: 기존 개발 실험과 같은 W36 스타벅스 사본. 규칙과 Qwen에 동일한 입력을 사용했다. 모델에게 카탈로그나 정답 후보를 보내지 않았다.

원시 모델 출력·날짜 표현·정규화·거부·카탈로그 후보와 보류 이유를 분리했다. 추출기·검증기·연결기 코드는 평가 중 변경하지 않았다.
평가 뒤 추가한 집계는 동결된 정답 후보에 이미 저장한 ‘유형 미확정 출시 언급 9건’을 별도로 센 것이다. 정답 후보나 모델 출력을 고쳐 성적을 바꾼 것이 아니다.

### 출시 사실과 최초 출시는 같은 질문이 아니었다

8월 5일 글은 코코 콜드 브루를 신제품이라고 명시하고 7월 27일 출시를 밝힌다. 신규·날짜가 함께 충분한 명시적 사건은 이 1건이다.
8월 18일 글에는 세 음료의 7월 27일 출시가 있지만, 각 음료가 최초 출시인지 복귀인지 본문만으로 확정할 수 없다.
8월 24일 글에는 매장용 선물 식품 6개의 8월 25일 출시/판매 사실이 있다. 제품 자체의 최초 출시인지 선물 포장·구성 변경인지는 불확실하다.
아몬드 정과 세트는 W33에도 같은 ID로 존재한다. 이번 발표를 제품의 첫 출시라고 읽으면 기존 카탈로그와 충돌한다.

따라서 **명시적 신규·복귀 유형과 날짜를 함께 요구한 엄격한 평가 1건**과 **유형 미확정도 포함한 제품별 날짜·출시 사실 평가 10건**을 나눴다.
10건은 문서별 언급이며 중복 제품을 합친 시장 상품 수가 아니다. 정답 후보에는 월 단위 일정, 과거 출시 회고, 온라인 예약 기간, 판매 채널 차이도 미확인 이유로 남겼다.

## 같은 입력으로 비교한 결과

| 항목 | 규칙 기준선 | Qwen 원시 출력 | Qwen + 코드 처리 |
|---|---:|---:|---:|
| 처리한 평가 문서 | 11 | 11 | 11 |
| 제품·유형·날짜 완전 일치 | 0/1 | 1/1 | 0/1 |
| 제품별 날짜·출시 사실 일치 | 0/10 | 1/10 | 0/10 |
| 충분한 날짜·출시 사실을 담지 못한 언급 | 10 | 9 | 10 |
| 원시 주장 수 | 6 | 20 | — |
| 근거 부족한데 신규/복귀로 단정한 주장 | 6 | 3 | 3 |
| 유용한 최종 계열 연결 | 0 | 연결 전 단계 | 0 |
| 근거 없는 최종 계열 연결 | 0 | 연결 전 단계 | 0 |

분모 1에서 1건을 맞혔다고 높은 모델 정확도라고 부르지 않는다. 이 정답 후보도 AI가 만들었다.
규칙 기준선은 전체 본문을 읽는 대신 같은 문단의 출시 단어·따옴표·명시 월일을 찾는다. 이 방식은 문단 사이 날짜 공유와 과거/이번 사건 구분을 놓쳤다.

Qwen 원시 출력에서는 근거 없는 구체적 날짜 3건과 promotion의 날짜를 출시일 칸에 넣은 2건이 있었다. 엄격한 평가표의 ‘유형/날짜 불확실’과 별도로 확인한 필드 오류다.
코드는 날짜 6개와 특징 4개를 보정/제거했고 주장 11개를 거부했다. 날짜 6개 중 5개는 null로 지웠고 1개는 9월을 8월로 계산했다.
삭제한 날짜에는 **모델이 정확하게 읽은 코코 콜드 브루의 날짜도 포함됐다.** 모든 보정을 품질 개선으로 세면 안 된다.

현재 W36 카탈로그에는 코코 콜드 브루가 없다. W33/W35에는 같은 제품 항목이 있지만 이번 기본 평가의 카탈로그 입력에는 포함하지 않았다.
따라서 날짜 검증만 고쳐도 이번 기본 입력에서 바로 유용한 연결이 생긴다고 주장할 수 없다. 과거 카탈로그 활용은 별도 연결 설계/평가가 필요하다.
유형까지 확정되고 W36에 연결 가능한 양성 사건이 없으므로, 연결기의 양성 품질은 이번 자료로 검증하지 못했다.

### 잘 처리한 사례: 쿠폰 사용이 출시로 바뀌지 않았다

[8월 10일 쿠폰 사용 현황](https://www.shinsegaegroupnewsroom.com/starbucks-in-the-heatwave/)의 블루베리 마블 치즈 케이크는 할인 쿠폰으로 많이 구매된 제품이다.
모델은 promotion, 출시 날짜 없음으로 읽었다. 코드는 카탈로그의 같은 제품 후보를 찾았지만 `not_explicit_launch`로 보류했다.
최종 출시 연결은 만들지 않았고 기존 새 발견 결과를 변경하지 않았다. 이는 오탐 방지 사례이며 유용한 출시 연결의 성공 사례는 아니다.

### 실패 사례: 모델의 정답을 코드가 지웠다

[8월 5일 콜드 브루 소식](https://www.shinsegaegroupnewsroom.com/starbucks-cold-brew-sold-a-lot-in-record-breaking-heat/) 3문단은 코코 콜드 브루의 신규 출시와 지난달 27일을 함께 말한다.
모델은 이를 신규·2026-07-27로 맞혔다. 그러나 개발 단계에서 만든 날짜 규칙은 ‘지난달 N일’을 지원하지 않아 `unsupported_body_date`로 날짜를 지웠다.
결과는 출시 날짜 미확인이고 W36 카탈로그 후보도 없었다. 모델의 추출 성공, 코드의 누락, 카탈로그 시점 불일치를 세 문제로 구분해야 한다.

다른 실패도 있었다. [추석 기프트 푸드 글](https://www.shinsegaegroupnewsroom.com/starbucks-chuseok-gift-food-launch/)은 제품별 사실을 제공하지만 모델은 상위 이름 하나를 promotion으로 만들었다.
날짜의 월을 코드가 바로잡아도 개별 상품 6개의 사실은 복원되지 않았다. ‘제목 5종’ 밖에 같은 날 출시한 14개입 제품이 더 있다는 점도 놓쳤다.

## 날짜 경계는 별도로 확인했다

평가 후 같은 추출기·모델을 튜닝하지 않고 AI가 만든 합성 문서 7개, 기대 항목 8개로 진단했다. 실제 11편의 성적과 합치지 않는다.

| 조건 | 원시 모델 → 코드 처리 |
|---|---|
| 두 제품의 서로 다른 날짜 + 별도 할인일 | 두 날짜를 각각 유지 |
| 8월 말의 ‘오는 2일’ | 9월 2일 유지 |
| 12월 말의 ‘오는 2일’ | 다음 해 1월 2일 유지 |
| 12월 말의 ‘오는 1월 2일’ | 모델이 같은 해로 잘못 읽음 → 코드가 지원하지 않아 날짜 삭제 |
| 과거 최초 출시 + 올해 복귀 + 행사일 | 이번 복귀 날짜를 유지 |
| 다음 분기 첫 영업일, 세부 날짜 미정 | null 유지 |
| 음력 날짜, 양력 미제공 | 문자열 `"null"`을 JSON null로 바꿈; 양력 날짜를 추측하지 않음 |

이 조건의 완전 일치는 원시 6/8, 코드 처리 후 7/8이다. 실제 모델 실행 1회씩의 결과이며 일반적인 날짜 해석 정확도가 아니다.
‘오는 N일’에서 통과한 연도 경계를 모든 상대 날짜가 지원된다는 뜻으로 확대하면 안 된다.

## 비용과 검토 부담

| 실제 문서 11편 | 결과 |
|---|---:|
| Qwen 호출 시간 합계 | 약 350.53초, 5분 51초 |
| 입력/출력 토큰 | 21,766 / 6,780 |
| 규칙 처리 시간 | 약 0.00031초, 모델 호출 없음 |
| 원시 주장 있는 문서 | 6편 |
| 검토할 원시 주장 | 20개 |
| 보정/제거 내역 | 10개, 원시 주장과 겹치는 내역 |
| 거부된 주장 | 11개, 원시 20개의 부분집합 |
| 보류된 카탈로그 후보 | 4개, 지원 연결 0개 |

위 검토 수를 더해 45개의 독립 업무라고 계산하지 않는다. 실제 사람의 검토 시간은 측정하지 않았다.
8월 18일 할인 행사 글 하나에 약 179.86초·출력 3,718토큰이 들었다. 모델은 9개 행사 제품을 길게 발췌했고 한 제품명의 ‘쉐이큰’을 ‘쉐이킨’으로 바꿨다.
같은 목록 발췌를 반복해 사용했기 때문에 9개 주장이 모두 원문 위치 검사에서 거부됐다. 또 다른 글은 의미 변경 없이 공백만 달라 발췌 검사가 실패했다.
무조건 긴 발췌를 생성하게 하는 것이 근거 추적 품질을 보장하지는 않는다.

행사 글을 통째로 생략하면 이 비용을 줄일 수 있을 것 같지만, 같은 글 안에 7월 27일의 제품별 출시 사실 3건도 있었다.
따라서 ‘행사 글은 전부 제외’는 이번 결과로 정당화되지 않는다. 다음 개선은 문서 전체의 종류보다 **제품별 출시 주장을 분리하는 것**에 초점을 둔다.

외부 추론 API 청구는 없었다. 로컬 기기 점유·전력·설치·사람 검토 비용은 무료라고 간주하지 않는다.
새 모델 호출의 변동성은 이번 최종 평가에서 반복 측정하지 않았다. 개발 단계의 동일 응답 반복 결과와 구분한다.

| 접근 변경/공식 발표 자동화 중단 | 가능하지만 자료에 유용한 사실 자체가 없었던 것은 아니다. 현재 결과만으로 소스 전체를 포기할 근거는 부족하다 |

가장 작은 다음 단위는 기존 문서의 제품별 주장·날짜 정밀도·유형 불확실성을 분리하고, 모델이 긴 문단을 다시 쓰는 대신 원문 위치를 참조하게 하는 것이다.
‘지난달 N일’과 연말 표현을 구분하고, 지원하지 않는 날짜는 날짜 없음의 이유를 보존한다. 카탈로그 연결은 우선 과거 관측을 포함한 후보 확인까지 실험하고 개별 온도·크기 출시 배지를 만들지 않는다.
새 프레임워크나 더 큰 모델을 먼저 도입할 근거는 얻지 못했다. 발표 유형이 불확실한 문제는 모델 크기만 키워 해결되는 문제가 아니다.

**다음 실험의 제안 기준**은 다음과 같다. 사용자의 제품 허용 오탐·누락 정책을 임의로 확정한 것이 아니다.

1. 현재 실패 문서를 회귀 자료로 삼아, 날짜 정답을 지우는 사례와 다른 제품의 날짜를 옮기는 사례를 제거한다. 이 자료의 결과는 개발 성적으로 표시한다.
2. 새로 승인한 기간에서 실제 날짜·제품별 근거가 충분한 사례를 확보한다. 같은 소스 자료가 너무 적으면 ‘근거 부족’으로 끝내며 좋은 기사로 교체하지 않는다.
3. 운영 도입 준비를 추천하려면 적어도 여러 문서의 **유용한 계열 연결 5건 이상**과 모호한 후보의 적절한 보류를 확인하고, 검토 표본에서 근거 없는 날짜·오연결이 없어야 한다. 이는 최소 표본 확인 조건이지 일반 정확도 보증이 아니다.
4. 검토할 후보 10개에 실제로 드는 사람의 시간을 측정하고, 사용자에게 부담을 감수할 가치가 있는지 판단받는다.
5. 한 번 더 개선해도 새 자료에서 유용한 연결이 없거나 충분한 근거를 계속 버리면, 이 자동화 경로를 멈추고 공식 근거 처리를 재설계하거나 새 발견 중심 운영을 우선하는 방향을 논의한다.

되돌릴 때는 연구 명령 호출을 중단하면 된다. 운영 파이프라인에 연결하지 않았으므로 수집·발행 경로를 되돌릴 필요가 없다. 승인 없이 main에 병합하지 않는다.

## 학습과 블로그 초안

시간표상 9월 10일에는 Git·통계·Python·REST API 관련 과목은 지난 일정이고 LangChain은 진행 중이다. 이는 일정 분류이며 사용자의 숙련도나 감상을 뜻하지 않는다.
이번에 Git의 fast-forward는 원격 데이터 이력을 잃지 않고 통합하는 데, 지문은 로컬 저장과 원격 보존·평가 입력의 일치를 확인하는 데 사용했다.
표본과 분모 구분은 1개의 명시적 신규 사건과 유형 미확정 9개 출시 언급, 실제 문서와 합성 사례를 섞지 않는 데 사용했다.
API 계약은 JSON 응답만 받는 것으로 끝나지 않았다. 날짜 칸의 문자열 `"null"`, 과거 사건과 이번 날짜, 모델 출력과 코드 보정을 별도로 다뤄야 했다. 단일 HTTP 호출과 파일로 충분해 LangChain은 추가하지 않았다.

### 초안: 모델을 검증하는 코드도 평가해야 한다

개발 기사 한 편에서는 공식 발표와 카탈로그의 메뉴를 연결할 수 있었다. 하지만 그 결과를 만들면서 프롬프트와 날짜 규칙을 고쳤기 때문에, 새 문서에서도 잘 된다는 근거로 쓰지는 않았다.

다음 실험은 제품 발표뿐 아니라 행사·교육·기부·금융상품 글을 포함했다. 기간과 상한을 정해 목록을 확보하고, 이미 읽은 글과 중복을 제외했다. AI가 만든 정답 후보라는 한계를 표시한 뒤 모델과 코드를 고정했다.

가장 뜻밖의 실패는 모델이 날짜를 틀린 곳이 아니었다. 모델은 ‘지난달 27일’을 맞게 읽었다. 개발 기사에 맞춰 만든 좁은 날짜 규칙이 그 답을 지원하지 않는다고 지워 버렸다.
모델이 다른 음료에 원문에 없는 날짜를 붙인 경우에는 같은 검증이 방어 역할을 했다. 검증이 있다는 이유만으로 결과 전체가 좋아졌다고 할 수 없었다.

긴 발췌를 남기는 설계도 비용이 있었다. 할인 행사 글 하나에서 9개 제품의 목록을 반복 생성했고, 한 제품명의 철자 차이 때문에 여러 주장이 함께 거부됐다.
행사 글을 버리면 간단할 것 같지만 그 안에도 실제 출시 날짜가 있었다. 결국 문서 전체를 분류하는 문제와 제품별 출시 주장을 추출하는 문제를 구분해야 했다.

현재 결과는 운영 도입을 정당화하지 못한다. 대신 어디에서 정보를 잃는지, 어떤 평가를 더 해야 하는지가 분명해졌다. 원문과 응답은 비공개 저장소에, 코드와 결정 근거는 공개 저장소에 나누어 보존했다.

**작성자 관점 자리:** 추가 개선에 학습 시간과 운영 비용을 투자할지, 이 결과를 보고 어떤 제품 우선순위를 택할지는 작성자가 적는다. AI가 사용자의 생각·감정·배움을 대신 만들지 않는다.

포트폴리오에는 사용자 결정(승인 범위·무료 로컬 모델 실험), AI 구현·검증, 실제 실패 분리, 두 저장소의 확인된 원격 커밋을 기록할 수 있다.
아직 ‘높은 출시 정확도’, ‘운영 시간 절감’, ‘완전 자동화’라고 표현할 성과는 측정하지 못했다.
