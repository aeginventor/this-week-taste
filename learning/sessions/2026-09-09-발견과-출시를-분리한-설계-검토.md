# 새로 보인 항목을 신제품이라고 부를 수 있는가

2026-09-09 · 조사와 첫 구현 묶음. 전면 검토는 진행 중이며 배포하지 않았다.

## 이번에 확인한 결론

현재 카탈로그는 실제 출시 이력보다 **각 사이트에서 관측된 목록**에 가깝다.
차집합 계산을 정교하게 해도 목록 등록일이 출시일이 되지는 않는다.
사용자는 새 발견과 공식 출시 확인을 구분하기로 결정했다.

첫 구현은 기존 관측 자료와 공개 ID를 보존하면서 이 구분을 코드에 반영했다.
공식 출시 근거를 수집·연결하는 경로는 아직 구현하지 않았다. 현재 새 필드는
`launch_status: unverified`이며 이것을 출시 확인 기능의 완성이라고 부르지 않는다.

## 확인 방법과 현재 흐름

AGENTS.md·CLAUDE.md, ADR 0001~0017, 관련 정찰·운영·학습 기록, pipeline·scrapers,
테스트, targets.yml, 기존 대화를 조사했다. 작업 시작 HEAD는 `543dbffd2fd1845b47937a6d43efcf157344263b`다.
이미 수집 시간·실행 주체·설정에 관한 미커밋 변경이 있어 그대로 보존했다.
변경 전 비교에는 HEAD 대신 **시작 시점 작업 트리의 diff.py·publish.py 사본**을 썼다.

```text
소스가 공개한 목록
  → snapshot: 원본 보관·항목 정규화·건수 검사
  → diff: 직전 비교 가능한 목록과 항목 매칭
  → enrich: 추가 후보의 공식 상세 설명·태그 보강
  → publish 안의 curate: 분류·요약·범위 밖 편집
  → 소스별 부분 파일
  → merge: 주간 JSON + 리포트
  → Next.js 정적 빌드
```

새 발견 검증은 publish의 LLM 호출 전에 추가했다. 기존 상품과 강하게 겹친 후보는
LLM에 보내지 않고 근거와 함께 보류한다. 설명 보강 요청을 이 단계보다 먼저 하는
기존 순서는 아직 남아 있어, 보류될 후보의 불필요한 상세 요청은 후속 개선 대상이다.

로컬 비공개 데이터에는 W33 4곳, W35 19곳, W36 18곳의 스냅샷이 있었다.
W34·W37 파일은 없었다. W36 homeplus는 W35 이월본이다. 현재 등록 표는 18곳이다.
카탈로그 전체라는 표현도 소스마다 다르다. homeplus는 온라인 배송 목록이고,
emart24는 FF·차별화 상품 범위다. 오프라인의 모든 판매 상품을 관측했다고 볼 수 없다.

## 주요 문제 후보 세 가지

| 문제 | 확인된 사실 | 아직 알 수 없는 것 |
|---|---|---|
| 목록 등장과 실제 출시의 혼동 | CU의 새 번호 2건이 이전 제품과 겹침. NEW 표시도 있음 | 이 제품들의 별도 리뉴얼·재출시 사실 |
| 과거·부분 산출물의 혼합 | 합성 사례에서 baseline 변경 뒤 옛 부분 파일이 병합됨. 이월 연쇄가 공백을 줄여 보임 | 운영에서 같은 오발행이 실제 발생한 횟수 |
| LLM 역할과 평가의 불일치 | 코드 역할은 분류·요약·범위 밖 판정. 문서의 재입고 판별·중복 병합은 없음 | 출시 정확도와 범위 판정의 실제 오류율 |

소스 라벨 일치율과 발행 다음 주 목록 이탈률은 진단 신호다. 독립적인 출시 정답이
없으므로 이를 정확도·재현율이라고 보고하지 않는다.

## 첫 반례: 건수는 같은데 선택한 상품이 달라졌다

W35 CU에는 `28057`·`28049`가 있었다. W36에는 이 번호가 남은 채
`28123`·`28108`이 추가됐다. 각각 옛 항목과 이름·바코드·가격이 같았다.
새 번호 두 개는 기존 W36 공개 발행본에도 포함돼 있었다.

변경 전 코드에 W35·W36 목록을 그대로 넣으면 added는 56건이었다.
두 목록의 배열 순서만 뒤집어도 56건이었지만, 위 두 쌍에서 선택한 번호가 바뀌었다.
바코드를 먼저 매칭하면서 이전 항목을 소비했고, 뒤늦게 나온 같은 원본 ID가
새 항목으로 밀려났다. 건수 테스트만으로는 보이지 않는 오류다.

선택한 구현은 [diff.py](../../pipeline/diff.py)의 원본 ID 전체 우선 매칭이다.
남은 항목의 보조 키는 양쪽에서 후보가 하나일 때만 자동 연결한다. 여러 후보를
구분하지 못하면 입력 순서로 고르지 않고 보류한다. 이름 유사도도 같은 원칙을 쓴다.
비교량 상한 때문에 매칭을 생략해야 하면 미검사 항목을 added로 넘기지 않고 실패한다.

[discovery.py](../../pipeline/discovery.py)는 과거 성공 스냅샷을 대조한다.
같은 원본 ID 또는 같은 소스의 바코드·정규화 이름·알려진 가격이 모두 겹치면 보류한다.
이름만 같거나 가격이 없는 경우는 자동 병합하지 않는다. 이 규칙은 물리적 동일성의
완전한 증명도, 재출시를 부정하는 판단도 아니다. 반례를 보수적으로 분리한 것이다.

## 사용자 결정과 AI의 판단

사용자가 선택한 제품·운영 정책은 다음 세 가지다.

1. 출시 확인과 새 발견을 구분해 제공한다.
2. 공식 출처가 해당 제품의 출시 사실과 시점을 명시한 경우만 출시 확인으로 표시한다.
3. 같은 주의 이전 성공본은 원본·판별 근거를 검증할 수 있을 때만 시점을 밝혀 유지한다.

AI는 전면 교체, 기존 diff 유지, 관측과 출시 판단 분리를 비교하고 세 번째를 첫 단계로
추천했다. Python·파일·정적 웹을 유지한 것은 최종 구조를 고정한 결정이 아니다.
새 수집 경로가 추가로 찾아내는 출시와 운영 비용을 측정할 수 있도록 기존 비교 기반을
먼저 신뢰할 수 있게 만든 선택이다. 대안 표는 [ADR-0018](../../docs/adr/0018-discovery-and-launch.md)에 있다.

사용자가 실제로 작성한 코드, 느낀 점, 이해한 개념은 이 기록에서 추정하지 않는다.
이번 조사·재현·구현·검증·문서 초안은 AI가 수행했다. 사용자의 기여는 문제 제기와
제품 정의·근거 기준·복구 정책의 결정이다.

## 복구 구현: 파일이 있으면 써도 되는가

합성 사례에서 이전 부분 파일이 남은 상태로 이번 diff가 baseline이 되면,
publish는 발행을 건너뛰었지만 merge는 그 파일을 읽었다.
W30 성공본을 W36까지 이월하고 W37에 복구한 다른 합성 사례에서는 공백이 1주로 나왔다.

[provenance.py](../../pipeline/provenance.py)는 SHA-256으로 파일 내용의 지문을 남긴다.
이것은 출시의 사실성 검증이 아니라 **기록 이후 입력이 바뀌었는지** 확인하는 장치다.
관측·원본·코드 → diff → 보강 → 부분 발행의 연결을 검사한다. 보강이 새 원본을
추가하는 것은 허용하되 이미 기록한 원본이 바뀌거나 사라지면 무효로 본다.

병합은 유효한 소스만 반영하고 제외 상태를 공개 주간 파일에도 남긴다.
재처리 실패가 전달된 소스의 이전 성공본은 `reused`로 표시한다. 단독 merge에서
실패 실행 정보가 없으면 `verified`라고만 표시하고 새로운 실행 성공으로 단정하지 않는다.
수집·생성 시각도 함께 남긴다. 유효한 소스가 하나도 없으면 기존 공개 파일을 보존하고 실패한다.

JSON 한 파일은 임시 파일을 완성한 뒤 교체한다. 주간 JSON과 리포트 둘을 동시에
바꾸는 트랜잭션은 아니다. 주간 파일을 마지막에 바꾸고 공통 generation_id로 불일치를
검출한다. 웹은 항목과 상태가 함께 있는 주간 JSON만 읽는다. 중간 장애 뒤 병합을
재실행하면 두 파일을 다시 맞춘다. [ADR-0019](../../docs/adr/0019-publication-input-integrity.md)

이월본을 성공 관측에서 제외해 기존 4주 비교 한도를 실제 성공 주차에 적용했다.
Makefile은 병합 실패를 성공 메시지로 덮지 않으며 `make -j`에서도 week 단계가 순서대로 돈다.
다중 프로세스가 같은 주차를 동시에 변경하는 운영은 아직 지원하지 않는다.

## LLM 경계에서 확인한 것

합성 응답 `out_of_scope: "false"`는 Python에서 참으로 평가돼 상품을 제외할 수 있었다.
숫자 blurb는 길이 계산에서 예외를 낼 수 있었고 중복 ref는 마지막 항목이 이겼다.
타입·중복 참조·채널 분류를 검사해 원본 폴백하도록 고쳤다. 편집 적용·거절·미사용
상태를 리포트에 남긴다. 테스트는 [test_curate_parse.py](../../tests/test_curate_parse.py)에 있다.

모델·프롬프트·출력 JSON 스키마는 바꾸지 않았다. 따라서 프롬프트 변경 시 의무인
실제 LLM curate_dryrun은 이번에 호출하지 않았다. 모델 요청·구독 사용량도 발생시키지 않았다.
응답 형식의 안전성을 검사한 결과를 모델의 내용 판단 정확도라고 해석하지 않는다.
W36 ‘프리미엄 바나나’, ‘데일리)맛배3입’은 범위 밖 오포함을 조사할 후속 표본이다.
이 재생에서는 기존 편집 결정을 고정했으므로 두 항목을 임의로 제거하지 않았다.

배포·이미지 URL 전수 검사·실제 수집 재실행은 수행하지 않았다.

## 사람이 실제로 하는 운영과 과거 문서의 정정

현재 발행 경로의 CLI는 `claude -p`다. 문서의 도구 이름만 보고 Codex API가
실제 백엔드라고 가정하면 안 된다. 구독 인증이 있는 로컬에서 발행을 실행하며,
데이터 동기화, 로컬 전용 소스 수집, 실패 리포트 검토, 병합·빌드·배포 확인 작업이 남는다.
이 사람 작업의 소요 시간은 측정하지 않았다.

2026-09-09에 GitHub 실행 기록을 읽으니 9월 7일 스케줄이 실제로 발화했다.
[W37 일반 슬롯](https://github.com/aeginventor/this-week-taste/actions/runs/34087684277)은
14개 소스의 diff를 완료했지만 compose·momstouch·parisbaguette·homeplus 때문에 최종 실패했다.
[다른 슬롯](https://github.com/aeginventor/this-week-taste/actions/runs/34108915963)도 실패했다.
‘자동화가 한 번도 돌지 않았다’는 과거 현황은 현재 사실이 아니다. 전체 실행 실패와
모든 소스 수집 실패는 구분해야 한다. 서버는 HEAD 코드로 실행됐고 로컬 미커밋 개선과 다르다.
