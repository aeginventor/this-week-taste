# 2026-08-25 — 소스 5개에서 15개로, 그리고 규칙 하나를 되돌린 날

아침에 소스 5개(cu·homeplus·starbucks·orion·compose)로 W35를 발행해둔 상태였다.
W36 발행은 8/31 월요일이라 6일이 비어 있었고, 그 시간에 무엇을 할지가 출발점이었다.

`ADR-0004`가 "수집은 발행 게이트를 기다리지 않는다"고 정해둔 덕에 답은 명확했다 —
**지금 붙인 소스는 W35를 기준선으로 갖고 8/31에 첫 diff가 나온다.** 미루면 한 주 밀린다.

> 결정 자체는 [`ADR-0013`](../../docs/adr/0013-source-url-optional.md)에 적었다.
> 여기는 그날 무엇을 몰랐다가 알게 됐는지를 남긴다.

## 1. 어제 만든 규칙을 오늘 되돌렸다

### 무엇이 문제였나

전날 밤 `.claude/skills/add-source/`에 이렇게 적어두었다.

> **개별 상품 URL이 있는지 먼저 확인한다 — 없으면 붙이지 않는다.**
> 7장이 "요약 + 원문 링크"를 요구한다.

그날 P0 소스 셋이 연달아 이것으로 막혔기 때문이다(이마트24 `href="#none"`,
메가 모달, 세븐일레븐 POST 전용). 같은 자리에서 세 번 시간을 버리고 나서
"이걸 먼저 보자"고 체크리스트에 넣은 것이다.

**규칙 자체는 합리적으로 보였는데, 7장을 잘못 옮긴 것이었다.**

### 무엇을 놓쳤나

7장의 실제 문구는 이렇다.

> ❌ 소스 사이트의 데이터를 **통째로 재배포하는 형태의 페이지** (반드시 요약 + 원문 링크)

금지 대상은 *통째 재배포*이고, 원문 링크는 그걸 피하는 **수단**이다.
그런데 우리가 발행하는 건 주당 수십~수백 건의 차집합이지 카탈로그 전체가 아니다
(전체는 비공개 저장소에만 있다, `ADR-0010`). **애초에 통째 재배포가 아닌데
수단을 요건으로 승격시킨 것이다.**

게다가 `CLAUDE.md` 4장은 처음부터 `source_url`을 nullable로 두고 있었다.
**스키마가 이미 "없을 수 있다"고 말하고 있었는데 내가 만든 체크리스트가 그걸 부정했다.**

### 계기

소유자가 물었다. "지금 소스를 못 긁어오고 있는 게 많아지는데 더 적극적으로 수집하는
방법이 없냐." 그래서 막힌 곳을 사유별로 갈라봤더니 이렇게 나왔다.

| 사유 | 소스 | 실제로 막혔나 |
|---|---|---|
| robots.txt가 금지 | 6곳 | **진짜.** 남의 금지다 |
| 봇 차단 403 | 투썸 | **진짜** |
| **개별 상품 URL 없음** | 이마트24·메가·세븐일레븐 | ← **우리 자체 규칙** |

**셋을 합치면 약 5,800건.** 그 규칙을 만든 날 우리가 수집하던 전체(7,116건)의 80%였다.
robots가 막은 6곳에서 얻을 것보다 **5배 많았다.**

### 이 날의 교훈

원칙을 체크리스트로 옮길 때 **수단과 목적이 뒤바뀌기 쉽다.** 원칙은 "통째 재배포 금지"인데
체크리스트에는 "상품 URL 없으면 금지"로 적혔다. 후자가 훨씬 검사하기 쉬워서다.

검사하기 쉬운 규칙이 검사하기 어려운 원칙을 밀어낸다. 그리고 그게 **더 엄격한 쪽으로만
틀리는 것도 아니다** — 이 경우엔 아무 근거 없이 소스 셋을 잘라냈다.

## 2. ID가 유일하다고 믿으면 안 된다 — 10곳 중 8곳에서 터졌다

`CLAUDE.md` 4장이 "추측하지 말고 실측할 것"이라고 경고한 자리인데,
그 경고가 얼마나 자주 맞는지는 오늘 알았다. 붙인 10곳 중 **8곳에서 ID 충돌**이 나왔다.
(충돌이 없던 둘은 교촌과 파리바게뜨다.)

배스킨라빈스 8건 · 던킨 2건 · BBQ 25건 · 이마트24 161건 · 맥도날드 10건 ·
bhc 45건 · 도미노 4건 · 맘스터치 4건.

**전부 전체 카탈로그를 뜬 뒤에야 보였다.** 한 카테고리만 보고 "ID 있고 유일하네" 하면
100% 놓친다. 자세한 것은 [`til/id-namespace-collision.md`](../til/id-namespace-collision.md)에 정리했다.

여기서 알게 된 것 하나 — **같은 "중복"이라도 대처가 정반대다.** CU는 *다른* 상품이 같은
바코드를 썼고(접으면 상품이 사라진다), 이마트24는 *같은* 상품이 두 번 실렸다(접는 게 맞다).
가르는 법은 "키가 같은데 **다른 필드도 같은가**"였다.

## 3. "값이 있다"와 "참이다"는 다르다

오늘 세 소스에서 같은 종류의 함정을 만났다.

```python
row["isNew"]                      # bhc — "Y" 또는 "N". "N"도 참이다
span.get_text()                   # 이마트24 — NEW 텍스트가 전건에 있고 opacity:0으로 숨긴다
subject.get_text()                # 도미노 — 이름 안에 label-box가 들어 있다
```

셋 다 **판정이 뒤집혀도 예외가 안 난다.** bhc를 truthy로 짰으면 158건 전부가
신상이 됐을 텐데, 로그에는 "라벨 158건" 이라고 찍히고 아무도 이상하게 여기지 않는다.

그래서 테스트에 숫자를 못 박았다.

```python
flagged = sum(1 for i in chicken if i["_labels"]["new"])
assert 0 < flagged < len(chicken)     # 전건도 0건도 아니어야 한다
```

이게 `CLAUDE.md` 7장이 말하는 **"틀린 답이 예외 없이 그냥 나오는 코드"**의 전형이다.

## 4. 정찰 기록은 믿을 게 못 된다

`sources/targets.yml`의 정찰 기록과 실측이 **여섯 군데** 달랐다.

| 소스 | 기록 | 실측 |
|---|---|---|
| 배스킨라빈스 | `/menu/fom.php`가 카탈로그의 일곱 번째 요청 | **캠페인 페이지.** 상품 링크 0개 |
| 던킨 | `3 COFFEE / 5 BEVERAGE / 6 SNACK` | **3 BEVERAGE / 5 SNACK / 6 COFFEE** |
| 던킨 | 응답 키가 `props.products` | COFFEE만 **`props.productCats`** |
| 교촌 | 탭이 `chicken` + `burger` | `burger`는 없다. `side`·`liquor`·`drink` |
| 이마트24 | `www.emart24.co.kr` | 302로 `emart24.co.kr`에 넘긴다 |
| 파리바게뜨 | `?cat1=` 순회로 250건 | **12건 미리보기다** |

정찰은 며칠 전에 한 것이고, 그 사이 사이트가 바뀌기도 하고 처음부터 잘못 읽기도 한다.
**기록은 어디를 볼지 알려주는 지도이지 측량값이 아니다.**

## 5. 실수 하나 — 정찰하다 파리바게뜨에서 503을 받았다

`base.Session`을 쓰지 않고 `curl`로 빠르게 13번쯤 던졌더니 503이 왔다.
5장이 요청 간격 1초를 요구하는데, **정찰이라는 이유로 그 강제를 우회한 셈**이다.

`base.Session`이 간격을 강제하는데도 정찰에서는 손으로 `curl`을 쓰게 된다.
편해서다. 앞으로는 정찰도 세션으로 한다.

덕분에(?) 얻은 것도 있다. 그 과정에서 정찰 기록에 없던 경로 둘을 찾았다 —
`admin-ajax.php?action=pb_get_product_list`(robots가 명시 허용)와
`/wp-json/wp/v2/product`(REST).

### 그리고 정찰 기록이 통째로 틀렸다는 걸 알게 됐다

서버가 진정된 뒤 다시 붙이면서 확인해보니, 기록의 **수집 방법 자체가 틀렸다.**

```
기록:  ?cat1=<카테고리> 순회 → 8요청 / 약 250건
실측:  ?cat1= 은 카테고리당 12건 미리보기.  /products/ 첫 화면은 8건씩.
      거기 박힌 data-total-count(45·30·49…)도 하위 카테고리 기준이다
```

**던킨 `/menu/all`(카테고리당 4건 미리보기)과 정확히 같은 함정**을 하루에 두 번 만난 것이다.
"목록 페이지에 상품이 보인다"와 "그게 전부다"는 다른 얘기인데, 정찰 때는 세어보지 않으면
구분이 안 된다.

진짜 경로는 `admin-ajax`였고 `data-total-count`가 **170**(브레드)을 준다.
REST의 카테고리 `count`도 170이라 **두 경로가 서로를 검증해줬다.**

최종: **519건 / 8요청.** 슬러그가 키로 중복 0건이고, `?per_page=100`을 서버가 존중한다.
그래서 `fetch_category`에 이런 검사를 넣었다.

```python
if total is not None and len(items) != total:
    raise ParseError(f"{len(items)}건을 받았는데 소스는 {total}건이라고 한다. "
                     "페이지를 놓쳤을 가능성이 높다.")
```

**소스가 스스로 밝힌 건수와 대조하는 것** — 미리보기 함정을 두 번 겪고 나서 넣은 방어다.

## 6. 커밋 메시지에서 기업명을 뺐다

소유자 지적. "커밋 목록을 볼 때 특정 기업 이름이 줄줄이 나오는 게 이상해 보인다."

```
feat: 컴포즈커피 스크래퍼   →   feat: compose 소스 추가
```

이유가 셋이다. 커밋이 실제로 건드리는 파일이 `scrapers/compose.py`라 **이름이 일치**하고,
`git log --grep=kyochon`으로 찾기 쉽고, 무엇보다 커밋 목록이 "어느 기업을 긁었는가"의
나열이 아니라 **"파이프라인에 뭘 붙였는가"**로 읽힌다.

이미 푸시된 11개는 `git filter-branch --msg-filter`로 재작성했다.
트리 해시가 동일한 것을 확인해 **내용은 그대로이고 메시지만 바뀐 것**을 검증했다.

⚠️ 여기서 걸린 것 — `git push --force-with-lease`가 `stale info`로 거부됐다.
`filter-branch`가 `refs/remotes/origin/main`까지 재작성해서 **lease의 기준이 오염**됐기
때문이다. 기준을 명시(`--force-with-lease=main:<원본해시>`)하면 통과한다.

## 7. 알림 경로를 실제로 한 번 돌렸다

`CLAUDE.md` 11장이 "한 번도 실행 안 됨"으로 적어둔 `alert.py`의 Issue 생성을
실제로 돌려봤다. 임시 데이터 디렉토리에 합성 W34 스냅샷(교촌 10건)을 놓고
실제 W35를 수집해 카테고리 건수 이상을 유도했다.

- Issue가 실제로 만들어졌다(#1, 확인 후 닫음)
- ⚠️ **예상이 틀렸다.** `pipeline` 라벨이 없어서 422가 날 줄 알았는데
  **GitHub이 없는 라벨을 자동 생성**했다
- 잘못된 토큰이면 401을 로그로만 남기고 파이프라인은 계속 간다
- 덤으로 **`_hold_previous`가 처음으로 실제 이월을 했다**(`held_from: 2026-W34`)

알림 장치는 고장 나도 **고장을 알려줄 수단이 알림뿐**이라 한 번은 실제로 봐야 한다.
